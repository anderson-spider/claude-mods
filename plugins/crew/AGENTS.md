# crew

Registers six subagent types in `session.start`, each `crew:<name>` with a default model and effort and a tool allowlist. A `prompt.compose` section (`crew:lead`, from `leadSection` in `agents.ts`) makes the main session the lead that delegates to them in waves (every independent piece in one message, unblocked work relaunched unasked, one line per update on what runs and waits) and counts a step done only after `crew:tester` or `crew:architect` verified it, sending a failure back to the same agent. The lead section is added only to a request whose tools include `Agent`, which no crew agent has, and it mentions Jev only when routing is on with a valid key. The plugin also carries the Flightdeck dashboard, vendored in `hooks/flightdeck/` (see Flightdeck below). With the `jevKey` option filled in (it is the only switch), Jev (TypeSafe) may move a call's model one step (the architect stays on Opus) and raise its effort to high. With the `nativeCodex` option and a loopback `ANTHROPIC_BASE_URL`, each role named there also gets a `crew:<role>-codex` twin on a Codex model (see Native Codex twins).

| Agent | Default model | Tools | Role |
| --- | --- | --- | --- |
| `code-reader` | haiku | Read, Grep, Glob | finds and explains code; returns `path:line` summaries |
| `research` | haiku | Read, Grep, Glob, Edit, Write, WebSearch, WebFetch, Context7, terminal-browser and Claude in Chrome tools | researches docs and the web, browses pages, writes findings and docs |
| `designer` | sonnet | Read, Grep, Glob, Edit, Write, WebSearch, WebFetch, Context7, terminal-browser and Claude in Chrome tools | specifies the UI and edits styles and layout |
| `developer` | sonnet | Read, Grep, Glob, Edit, Write, Bash | implements a spec and runs its tests |
| `tester` | sonnet | Read, Grep, Glob, Edit, Write, Bash | reproduces, writes tests, runs the suite; writes test files and `.crew/reviews/**/*.md` only, never production code |
| `architect` | opus | Read, Grep, Glob, Write, Bash | plans and reviews; answers with a one-line verdict (the dashboard's ARCHITECT panel shows it) then the path; writes `.crew/**/*.md` only, never code |

A twin is its base row with a Codex model id and a one-line description; prompt, tools and effort are the base's.

## Layout

```
plugins/crew/
  .claude-plugin/plugin.json
  commands/panel.md           `/crew:panel`: only a fallback body (`disable-model-invocation`); the `command.run` hook answers it
  hooks/hooks.json            points to register.tsx
  hooks/register.tsx          $.agent.register in session.start (the six, then the registered twins: `Native`, `registerNative`), the call to `registerFlightdeck`, the lead's prompt.compose sections (`crew:lead`, and `crew:native-codex` for the registered twins), the Write/Edit guard, the agent.spawn and turn.step hooks of Jev routing
  hooks/flightdeck/           vendored Flightdeck: register.tsx (`registerFlightdeck`), core.ts, rail.tsx, elapsed.tsx, LICENSE, NOTICE.md
  hooks/agents.ts             SPECIALISTS: name, description, prompt, model, effort, tools; MODEL_FLOORS; EFFORT_FLOOR; leadSection; `Agent<M>` (a specialist is `Agent<Model>`), NATIVE_SUFFIX, isLoopbackBase, nativeCodexSpecs, nativeCodexSection
  hooks/guard.ts              deniedWrite(type, path): the lane of each agent; `laneRole` maps a `-codex` twin to its base role
  hooks/native.ts             `parseCodexModels`: the `role=model` parser of the `nativeCodex` option (never throws; what it cannot use comes back as errors)
  hooks/jev.ts                Jev client: one 3 s deadline, one retry, breaker, cap of 4 calls in flight
  hooks/questions.ts          the two questions (tier, reasoning_depth), the pinned Jev model and the thresholds
  hooks/routing.ts            which calls are routable (`Target`: a specialist, or a registered twin with `base`), state for Jev, answers to model and effort, what moved and the notice text
  hooks/effort.ts             pending and bound effort per subagent id; `bind` returns what happened to the effort
  hooks/confirm.ts            first-step check of a routed subagent: what ran (API model id, effort sent) against its tag; `normalizeModel`
  hooks/decisions.ts          decision log: the record (model fields are strings), its file name, FNV-1a hash of the description; the write is injected
  hooks/key.ts                the `jevKey` check and `resolveAccess`: key, trusted home and why routing is off
  hooks/redact.ts             secrets, emails and paths removed from text before it is sent
  skills/brainstorm/SKILL.md  how to plan with the agents
  types/index.d.ts            the dashboard's state under `crew` (named in plugin.json `types`)
  tests/                      a test file per module (`questions.test.ts` only checks the constants), `native.test.ts` for `parseCodexModels`, and the register tests through the host; flightdeck.test.ts is upstream's on `hooks/flightdeck/core`, plus the panel command's pure tests
```

In the project where the agents run, everything they write lives in an unversioned folder, which the brainstorm skill adds to `.gitignore`:

```
<repo>/.crew/
  plans/<name>.md       the plan the user approves (brainstorm, step 5)
  reviews/<name>.md     the architect's reviews (the tester's reports: <name>-test.md)
  research/<name>.md    the research agent's findings
```

## Brainstorm flow

`.crew/` ignored (step 0) -> frame -> `code-reader` and `research` in parallel -> options (`designer` first for UI) -> `architect` challenges the leading option -> plan in `.crew/plans/` (each step with its owner, dependencies, files and state, ending in waves of steps that can run together), approved by the user -> recommendation of `/goal` (verifiable end), `/loop` (repeating or waiting work) or direct execution, never started by the skill -> `developer`, `tester`, `architect` audit, run by waves; a step is verified by someone other than its implementer, and a failure goes back to the same developer. No edits happen before the approval.

## Jev routing

Off until the `jevKey` option is filled in; nothing is sent or read without it. On an `agent.spawn` of a `crew:<name>` type from `SPECIALISTS` (or a registered twin, for its effort only), Jev answers one request with a `tier` choice (haiku, sonnet, opus) and a `reasoning_depth` score; the plugin rewrites `model` and, on the subagent's `turn.step`s, `effort`.

- The agent type is never rewritten: each agent keeps its lane and tools.
- Untouched, with no request: another type, a fork, a workflow script's agent (a hook can only refuse that spawn, so a rewritten model would be ignored: no model, no effort), a call that already names a model (except a Codex twin's named in `nativeCodex`, which the `agent.spawn` hook denies), no `jevKey` (`enabled` is false from `register` on, so no settings are read), a `jevKey` that is not a valid key (a debug line says so once), a repository that declares `jevKey` in its project or local settings (a debug log line says so once), and repository settings that cannot be read.
- Twins: routable only when registered this activation (`Native.registered`, not the option), and then for effort only: the decision's model is the twin's own id and `moved().model` is undefined, so no `model` is sent whatever the tier answer says. Jev is asked about the base role (`stateOf` sends `base`), and effort follows the base role's rule and thresholds.
- Tier: applied from confidence 0.5, else the default. Model and effort are clamped to the default one step either way; the architect is never below opus (`MODEL_FLOORS`, so its model stays `opus`) and no agent's effort is below medium (`EFFORT_FLOOR`). Effort: depth from 3.0 is high, below it medium, then raised to the floor (so below 3.0 keeps `medium` and only a high depth moves it, to `high`); a depth within 0.01 of 3.0 keeps the default. The thresholds are a declared policy, not a fit: 3.0 on Jev's 0-4 scale keeps `high` for the top band (about 30% of the 126 decisions logged when it was set, against about half at 2.5: a snapshot), and the tier applies from confidence 0.5. The decision log and the debug log are where to revisit them.
- Fail open: no key, an error status, a malformed body, a timeout, an open breaker or a fifth concurrent call leave the call as it came. One 3 s deadline covers both attempts; a retry (429, 5xx, dropped connection) needs one second left.
- Key: the `jevKey` option only, and it is the switch (`checkKey`: a string, trimmed, `/^[\x21-\x7e]{1,512}$/`; empty is off silently, anything else invalid is off with one debug line that never shows the value). `enabled` is computed in `register` from the option, so with no key `prompt.compose`, `agent.spawn` and `turn.step` return at once and read no settings; `turn.step` never awaits the settings. With a key, `resolveAccess` reads the project and local settings once (`$.settings.read`) and turns routing off when they cannot be read or declare `jevKey` under `crew` or `crew@*`. `HOME` (`$.env.get`) is trusted only when those settings do not declare it and it is absolute (redaction applies the same rule to the `~` it strips); when none is trusted, redaction takes `/Users/<name>` or `/home/<name>` from the session's directory (never the repository's `HOME`) so the username and the dashed home still go. A stale `jevRouting` in the stored options is ignored (the load survives; the engine refuses a non-string `jevKey` before `register`). A change to any option reloads the plugin (the dashboard's options too), so the key and the lead section are resolved once per activation, and the effort book, the pending confirmations and the breaker start empty after one: a routed subagent's later steps run on the host's effort until it ends. The key goes only in the `Authorization` header; errors and logs carry a status or a reason, never a body, a key or a prompt.
- Sent: the agent name, the call description and the prompt, with secrets, emails and paths removed, the prompt cut to 4000 characters, to `https://api.typesafe.ai/v1/systemone` with the model `jev-1.13.0`.
- Effort: every routable call has an entry under its type, description and spawning loop before the spawn continues, holding the default effort when Jev changed nothing or failed, so two calls alike with different efforts leave both on their defaults instead of trading them. A default entry only counts in that rule: it is never applied to a step, so a call that Jev changed nothing on or failed on keeps whatever `effort` the host sends. An unknown `agentId` on `turn.step` reads `$.agent.list()` once and matches it (an entry that names a parent matches only an agent of that parent, when the list gives one). The id is bound when the spawn resolves. Entries stay (64 at most) so a resumed subagent keeps its effort. The step is left alone when `e.effort` is absent. An id's effort never changes once a step has gone out (one exception, below), because a top-level `effort` change between requests invalidates the cached message blocks ([effort](https://platform.claude.com/docs/en/build-with-claude/effort), [prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching); a per-message effort keeps the cache, and the plugin cannot see which way the host sends it); only three cases still change a running subagent's effort and restart its cache: an option change that reloads the plugin (later steps run on the host's effort), the exception below, and a resumed subagent whose entry was evicted after 64. A bind that runs while the list is being read is honored by the step that was waiting. An id that stepped before its effort was known (not listed yet, the list failing, every entry already taken, or ambiguous) keeps its default for its run, while an id stepping with nothing pending is not recorded at all (the one exception to that rule: an already-running agent of the same type and description with no entry of its own, such as one spawned with an explicit model or before `/reload-plugins`, can take a pending entry on its next step), and a bind that finds the id already on the entry's effort reports it as matched; a bind that finds its entry already matched by another agent's step leaves that agent as it is and gives the routed id the effort only if it has not stepped. Ids and entries are bounded by recency: a hit refreshes its place. Ids no list names (a workflow's agents, forks) are never kept in the book beyond the entries that are pending. Verified live: subagents ran on the routed model and on an `effort` above the default (their transcripts carry both).
- Rate limit: the cap of 4 counts requests, not deadlines. `$.http.fetch` cannot be aborted, so a slot stays held until its fetch settles even after the call failed open at the deadline, and for 60 s at most: a fetch that never settles frees its slot then (`SLOT_HOLD_MS`). The Jev model id in the log is kept only when it matches `[\w.:-]{1,64}`.
- Visibility: a routed call's `description` is rewritten to `<description> · <model>/<effort>` (Jev's decision, kept or moved; a call Jev failed on keeps its own; a trailing tag already in the description is stripped first (only a tag the plugin could have written: an alias, or the id of a registered twin, matched literally, so `docs · v2/high` stays), so it is neither sent nor doubled; a kept model is shown although no `model` is passed, the agent's own default being that model; a twin shows its Codex id), so the task list shows the choice; the effort book matches that rewritten description, and the decision log hashes the original. An effort that did not take still shows the planned one there; the notice says it was not applied. Once the spawn resolves with an agent id (a refused spawn announces nothing), a `$.ui.notice` per decision and a debug log line with tier, confidence, depth, the effort that was applied (or the default), Jev model id and duration (never the prompt). An effort that was not applied (its entry lost the race to the first step, or was ambiguous) shows the default in the notice with "effort <x> not applied" and gets its own debug line with the outcome.
- Confirmation: the first `turn.step` of a routed subagent that the API answered (`usage` present; a failed step leaves the check for the next) and that ends after its spawn resolved compares the model id the API reported (`usage.model`) and the effort sent with the tag (an alias matches the Claude id that contains it; any other id must equal the planned one after `normalizeModel`, or be its dated release, `-YYYY-MM-DD` or `-YYYYMMDD`, so `gpt-6` does not accept `gpt-6-mini`), and logs one transcript line (`$.ui.log` `to: 'transcript'`; `$.ui.notice` is closed by then): `jev: <description>: confirmed <model> · <effort>` (the host shows it after `crew:`) or `ran <model> · <effort>, not <model>/<effort>`. It then rewrites the decision file with `ran: { model, effort }`, after the spawn's own write, waiting for both about 1 s at most (`settleDecision`) so a hung write cannot hold the step. The line carries the call's description, and like every `$.ui.log` line it also goes to the debug log. Pending checks are kept for 64 agents at most.
- Decision log: with a key set (no option of its own), one JSON file per routed decision in `<trusted home>/.claude/crew/decisions/`, named `<ISO ts with ':' as '-'>-<agent id>.json`, written with `$.fs.write` where the notice is emitted, also when nothing changed (so keeps show), and not for a refused spawn or a call Jev failed on. The home is the one resolved with the key (`access.home`), never the repository's `HOME`; without one nothing is written and one debug line says so. The record (`v: 1`) has `ts`, `agent`, `tier`, `confidence`, `depth`, `defaultModel`, `model` (strings: an alias, or a twin's id), `defaultEffort`, `effortPlanned`, `effortApplied` (what the subagent runs on), `bind` (the effort book's outcome), `jevModel`, `durationMs`, `descriptionHash` (FNV-1a of the description: a non-cryptographic hash that a short, common description can be guessed from), `applied`, `ran` (null until the confirmation rewrites it) and `outcome: null` for hand annotation; never the prompt, the description, the key or a path. The write starts before the notice and is awaited for about 1 s (`$.clock.after`, cancelled when it settles) before the spawn's result returns; it never rejects (a failure is one debug line), and one still pending then is one debug line, "decision write slow", and keeps running, so it cannot change the result or hold it. The host has no delete or append (`$.fs` has read, write, list, exists, stat), so the folder is not pruned: about 400 bytes of JSON, one file each (a disk block on most file systems). Verified live: `$.fs.write` is allowed under the home, outside the project (records are written there); an `fs.*` hook of another plugin may still refuse it, and the failure is only the debug line.

## Native Codex twins

Off until the `nativeCodex` option names a model (`role=model` pairs, parsed by `parseCodexModels` in `hooks/native.ts`; what it cannot use is one debug line). A twin is `crew:<role>-codex` (`nativeCodexSpecs`): the base role's prompt, tools and effort on the given model id, a one-line description, run by the host as an ordinary subagent through the proxy at `ANTHROPIC_BASE_URL` (a local proxy, such as the codex-models plugin; what a twin reads and writes goes to OpenAI through it).

- Gate: `session.start` registers the twins only when `$.env.get('ANTHROPIC_BASE_URL')` is an `http:` URL whose host `isLoopbackBase` accepts (127.0.0.0/8, `::1`, `localhost`, in the forms `new URL` normalizes to them; not `https:`, `0.0.0.0`, `::ffff:` forms, a trailing dot or a lookalike name). Otherwise none is registered and one debug line says so. One refused registration leaves the others; its own `try` keeps the dashboard starting.
- Registered set: `Native.registered`, filled by `session.start`, is what routing and the `crew:native-codex` section read, not the option (the `model` refusal below reads the option). A twin never registered gets no Jev request and no section.
- Section: `crew:native-codex` (`nativeCodexSection`) is its own `prompt.compose` section, under the same `Agent` rule as the lead's; `leadSection` stays free of Codex. It lists the registered twins, says they are ordinary Agent calls with the base role's tools and write lane (never pass `model` to one), says a twin counts as someone other than the implementer when a Claude agent built the change (and the reverse), and says a failure goes back to the same twin.
- Lanes: `laneRole` strips `-codex` when what is left names a specialist, so a twin has its base's lane (`crew:tester-codex` writes test files only). A `crew:` type ending in `-codex` whose base is no specialist has no lane and every write is held (fail closed). Another plugin's `<x>:tester-codex` gets the base lane too, as `<x>:tester` already did.
- Jev: effort only, never `model` (see Jev routing). Confirmation reads the id the proxy reports with `normalizeModel`: lower case, without `[1m]` or a trailing `-low|medium|high|xhigh` or `:effort`, then equal to the planned id or its dated release.
- Dashboard: `crew:architect-codex` matches `architectPattern`, so it shows in the ARCHITECT panel as a consult; `crew:developer-codex` is a card.
- Model: the `agent.spawn` hook denies a call to a twin the option names (`Native.specs`, not the registered set) that passes `model` (the parameter would win over the twin's definition and run it on Claude, untagged and unconfirmed), with a message to call again without it; the section tells the lead the same. It does not depend on registration: a later `session.start` where the env read or a registration fails empties `Native.registered` while the host keeps the types, and an unregistered type is rejected by the host anyway. A base role with `model` is untouched.
- Repeated role: a role named twice in `nativeCodex` keeps the last pair (`parseCodexModels` builds a map).
- Unverified live: that Claude Code sends `effort` on a step of a non-Claude model id. The step hook only rewrites an `effort` the host already sends, so if it sends none, Jev's effort for a twin is planned, tagged and announced but never reaches the subagent.
- Reload gap: an option change reloads crew without a `session.start`, so `Native.registered` starts empty: the twins are not routed and their section is gone until the next session.
- The twins are ordinary subagents run by the host; they need no Codex CLI and have no sandbox of their own.

## Flightdeck

`hooks/flightdeck/` is Flightdeck 0.3.2 (MIT; `LICENSE` stays, `NOTICE.md` lists every local change and its origin). It adds the panel, the `/crew:panel` command (`commands/panel.md`, which replaces upstream's `/flightdeck`), the status line and thirteen options in `plugin.json` (upstream's twelve with their names and defaults, and `placement`; a saved `flightdeck@claude-flightdeck` option does not carry over, and the two plugins must not be installed together). The pane keeps the id `flightdeck` and the title `Flightdeck`. Keep the vendored files close to upstream so a new release can be diffed against them.

- One hooks module: `hooks.json` points only to `register.tsx`, which calls `registerFlightdeck(on, options)` from `hooks/flightdeck/register.tsx`. The engine refuses a second module, and `$` is not followed across an import, so the dashboard's hooks keep their `$` calls in that file.
- Order in `register`: the crew's `session.start` hook comes first, then `registerFlightdeck`, then the crew's `prompt.compose`, `agent.spawn`, `turn.step` and `tool.call` hooks. In one plugin the first registration is the outermost: the crew registers its agents before the dashboard runs, and the dashboard wraps the spawn (it sees the description and model as they came), the step and the write (it logs the guard's refusals).
- `session.start`, `agent.spawn` and `turn.step` take the empty matcher `{}` on the crew's side: the engine refuses two hooks on one event without a matcher in one plugin. `tests/register.test.ts` covers a spawn that Jev routes and the dashboard shows.
- Every Flightdeck hook that calls `next` (all but the terminal `command.run` and the Pane `ui.render`) observes and never throws: it keeps its own work in `try/catch` and returns what `next` returned (or `next(e)`). A failure there would skip the crew's hooks on the same event (no agents registered, the guard's refusal turned into a generic hold). Add no pass-through `.catch` to them: it lets a write through that the guard could not check.
- State is owned by `crew` (the thirteen dashboard atoms in `hooks/flightdeck/register.tsx`; `types/index.d.ts` and `plugin.json` `types` name them). Any plugin can read it, and nothing is written outside the session except the panel choice in `$.store`.
- `validate` lists `gating hook without .catch` for the dashboard's hooks; that is intended.

### The panel command and band

- `/crew:panel [on|off|side|prompt|reset|layout auto|compact|wide|mini]` is a markdown command (`disable-model-invocation: true`) answered by `on('command.run', { command: 'crew:panel' })`, which returns `{ text }` without `next`. Its `.catch` answers a fixed text, so a failure never falls through to the markdown body (which only tells the person to run `/reload-plugins`). `parsePanelArgs` (`core.ts`) reads the arguments; anything outside the grammar answers `PANEL_USAGE`.
- Bare toggles. `on` shows the panel at the current placement and `off` hides it, closing the pane. `side` shows the host pane (`$.ui.open`, id `flightdeck`); `prompt` closes the pane and shows the plugin's own band above the prompt. `layout` sets `view.layout` for the side pane; in prompt mode it opens no pane. `reset` clears the dashboard's state (`resetAll`, as on `/clear`) and leaves the choice alone.
- The choice is `{ isVisible, placement }`. The `panel` atom is the session's effective choice and drives the band's redraw; `$.store` key `panel` (`{ v: 1, isVisible, placement }`) is the person's pick across sessions, written only by `/crew:panel` and by a person's close of the pane (the `ui.close { id }` hook saves hidden on origin `person`; origin `plugin` and `unload` save nothing). The atom is written first, then the store; a store write that fails logs one debug line and the session's choice stands.
- `session.start` seeds the atom in its own `try`, after the dashboard's other start work: the stored pick (`storedChoice` reads it leniently; a store that fails or holds anything else counts as no pick), else `{ isVisible: openOnStart, placement }` from the options. It opens the pane only when the choice is visible at `side`. An option change mid-session reloads the module without a `session.start`, so it applies from the next session or the next `/crew:panel`. A null atom (start not yet run) leaves the band out.
- Bare `/crew:panel` in side mode reads whether the pane is shown from `$.ui.panes()` (`isPlaced`), so an unasked pane waiting undrawn on a narrow terminal counts as hidden; it falls back to the choice when the call fails. In prompt mode it reads the choice.
- The band is `on('ui.render', { component: 'AbovePrompt' })`. It reads the atom before any early return (a hook redraws only for what it read), and passes with `next(e)` on a survey, a hidden panel or `side`. Otherwise it awaits `next(e)` and returns that tree when it is not `type: 'engine'`: another plugin's band (branch-guard's held commit) wins whichever plugin sits above, and the band never wraps one. Over the engine's own empty band it draws `drawSummary`, the pane's mini summary, sized to `bodyColumns`, with at most `min(3, max(1, maxRows - 5))` live cards; a draw that fails returns the tree below. The surface raises `AbovePrompt` on terminal and desktop only, so `prompt` shows nothing on vscode or mobile and does not fall back to the pane.
- `drawSummary`, `loadDeck` and `makeClock` are module-level in `register.tsx` and shared by the Pane (layout `mini`, or `auto` inline) and the band. Functions that take `$` (`pickedChoice`, `currentChoice`, `setChoice`, `isShown`, `openSide`) are declared at the top of that file: `validate` refuses `$` passed to anything else.

## Notes

- `effort` is set on purpose: every agent defaults to `medium` (Opus 5.5 and Haiku 5.5 default to `medium`, Sonnet 5.5 to `high`), and routing may raise it to `high` but never lower it below `medium` (`EFFORT_FLOOR`).
- Prompts say what to do and why, not lists of prohibitions; keep new ones short and test a removal before adding a line.
- `hooks/agents.ts` is pure (`SPECIALISTS`, `MODEL_FLOORS` and the `leadSection` text); `hooks/register.tsx` holds the two `$.agent.register` calls (the six specialists, the twins) and every other `$` call except the dashboard's (those are in `hooks/flightdeck/register.tsx`), which it passes to pure modules as injected functions.
- Models are aliases (`haiku`, `sonnet`, `opus`), so they follow the newest model of each family. Routing moves a call between them and never to `fable` or a full id; a twin's Codex id is the one exception to aliases, and routing never moves it.
- `tests/agents.test.ts` checks the table; `tests/register.test.ts` runs `session.start` through the test host.
- Browser and MCP tool names are listed explicitly (no wildcard); one a session does not have connected is unavailable to the agent.
- Names stay short and avoid "advisor" and "architect" except for `architect` itself: the dashboard shows the type (`crew:<name>`) on a narrow card and files any type matching its `architectPattern` under its architect panel, not as a card. `architect-codex` is a second intentional match.
- `architect` is named so on purpose: it matches the dashboard's default `architectPattern`, so its runs show in the ARCHITECT panel as consults, not as cards. The panel shows the first non-empty line of the architect's answer, so the prompt asks for a one-line verdict first.
- `hooks/guard.ts` holds the write rules and `register.tsx` enforces them in a `tool.call` hook on `Write` and `Edit`: the architect may write Markdown under `.crew/` only (plans and reviews, unversioned; the brainstorm skill adds `.crew/` to the root `.gitignore` when it is not ignored), the tester test files and Markdown under `.crew/reviews/`, and a path with a `..` segment is refused for both. The hook finds the caller through `e.agentId` and `$.agent.list()`, never blocks the main loop, and holds a subagent whose write it could not check.
- Not enforced, prompt only: the designer leaves logic and tests alone, and the architect's and tester's `Bash` is not screened for writes.
- `skills/brainstorm/SKILL.md` tells Claude how to plan with these agents (frame, gather in parallel, diverge, challenge with `architect`, plan); keep its agent names in step with `hooks/agents.ts`.
