# Pantheon

A Claude Code mod in the style of [oh-my-opencode-slim](https://github.com/alvinunreal/oh-my-opencode-slim): the main Claude session is the lead and delegates to specialists, each a native Claude subagent. The configuration chooses each role's and council seat's model and effort.

## Install

```
/plugin marketplace add anderson-spider/claude-mods
/plugin install pantheon@spider-claude-mods
```

`/pantheon doctor` checks the configuration and pings every role and council seat by asking the session, after the report, to call each `pantheon:*` agent, so they show as `pending` in the report. Disabled roles and seats show as `off`.

## Roles

| Role or seat | Default model |
| --- | --- |
| code-reader | `haiku` |
| docs-reader | `haiku` |
| developer | `sonnet` |
| architect | `opus` |
| qa | `sonnet` |
| ux | `sonnet` |
| git | `haiku` |
| seat alpha | `opus` |
| seat beta | `sonnet` |

The lead calls a role with `Agent({ subagent_type: "pantheon:<role>", prompt })` and a seat with `pantheon:councillor-<seat>`.

The lead gets a system prompt section, adapted from the slim `orchestrator.ts`, that says when to delegate, how to parallelize and how to call each role. A disabled role leaves that section and the Agent tool.

The `code-reader` role maps the codebase and returns compressed context. The `docs-reader` role reads external documentation and research and does not write docs. The `architect` role covers architecture, debugging, code review and simplification, read-only.

The `qa` role runs what was built (commands and tests, the app, a herdr pane when one is available, error paths) and returns a verdict per acceptance criterion, `C<n>: pass|fail — <evidence>` lines and a final `QA: pass|fail`; partial coverage is a fail. It never fixes code, never runs side effects (deploy, publish, push, migrations against shared data) and writes only in the session scratchpad, through Bash: Edit, Write, NotebookEdit and Agent are withheld. The lead routes acceptance criteria verification to it.

The `developer` role writes all the code (backend, scripts, tests, hooks, CLI, UI code and logic) and runs scripts, test batteries and API calls within the lead’s brief, returning short results (status, tables or errors). It does no external research or sub-delegation. When a task is about look and feel it tells the lead that it belongs to `ux`, as guidance, not a refusal. Once its checks (or its own validation) pass, it commits only its task's files with explicit paths (`git add -- <paths>`, then `git commit -- <paths>` with the task id in the message), never with `-A`, `.`, `--no-verify` or `--amend`, and never pushes, rebases, resets, merges, switches branches or stashes. The lead pushes.

The `ux` role owns the look and feel (layout, hierarchy, color, spacing, motion, affordances and UI copy) and implements it in whichever files its brief or task assigns. When the direction is open it first makes mockups (text for terminal UI, throwaway HTML prototypes in the scratchpad for web or desktop UI, never committed) and offers two or three directions; it implements the chosen one, with the design criteria (typography, color, motion, composition) and UI review. It commits its own task like `developer`. The split between the two is by kind of work, not by file extension.

The `git` role handles squash and PR/MR creation after validation, and repository state changes such as checkout, switch, worktree and stash. The lead decides and validates; its brief specifies the included changes, branch, base, squash and PR/MR choices, and the task's commit range for history rewrites. Git reads status and diffs, preserves unrelated changes, follows commit conventions and PR/MR templates, uses `gh` or `glab` for the remote, and reports commit SHAs, the PR/MR URL and refusals.

Its fixed refusals cover modifying default or protected branches (including main, master, develop, release and release/*), unverified branch protection, force push without `--force-with-lease`, PR/MR merges, remote branch deletion, history rewrites outside an explicit task commit range, and work outside the task.

### Commands

- `/pantheon` opens or focuses the panel, which also opens by itself at session start.
- `/pantheon close` closes the panel.
- `/pantheon config` (effective config, where each field came from, current error) and `/pantheon doctor`.

## Panel

The panel keeps nine role slots in order: lead, code-reader, docs-reader, developer, architect, qa, ux, git and council. Running lists one row per live instance (parallel runs each get a row, and each council seat has its own); Idle lists exactly one row per role and council seat with nothing live, showing the latest run's model, duration and task plus a strip of `▰` marks for the role's last four rounds, shown only from two rounds on (green done, red failed, `+N` for older ones). Disabled roles and seats show as `⊘` rows, and a lost run counts as Idle. Groups fold to their headings when the pane is short. Other native subagents appear under "other agents" when present. Running rows show model, elapsed time, context use and last activity; roles that never ran leave the time and task blank and keep their role color; when a role last ran shows in the timeline and the mini view. A "Session log" card at the bottom lists the last eight events (round started, done, failed, lost or stopped, disabled roles) with the time and the role in its color; end lines name the task, so parallel runs of one role stay apart; it is the first card to drop when the pane is short. The lead shows its model, effort, turn clock, context and the roles it is delegating to.

The desktop panel follows the former hud plugin's dark palette, tinted segments and 6px corners. The header, session card, agent groups and timeline share a 24px inset; the timeline follows the available pane width. Cost, Tokens and Time are horizontal segments below the session card, with fixed numeric slots (9, 7 and 6 cells); they wrap on narrow panes and become plain label/value rows when an individual segment cannot fit, stacking the value below the label at the smallest widths. Cost comes from the host's ledger and reads `—` until a measurement arrives. Tokens adds each agent's context or input and output, so it is a rough size, not a bill. Collapsible Running and Idle groups use full-width hairline separators. Each desktop row leads with role and model, followed by the task and readings; its state marker has a fixed slot. Planned text uses the readable secondary color. Native text and buttons sit over static SVG backgrounds, so they remain selectable and actionable.

The terminal panel draws one bordered card per section, each with its own border color, task-first rows, context progress bars and one-line Cost, Tokens and Time readings. Its close button appears from 58 columns. A rail animates at 110 ms only while an agent has active work, and clocks tick live.


The footer reads `keys: esc close`. The header shows `working` while only the main session runs, and the running-agent count when roles are active.

The terminal panel docks beside the transcript and uses a mini view when placed inline. Desktop adds a "Last 15 minutes" SVG timeline with a lane per role. The lead lane draws completed turns in gray and the current running turn in white; completed turns are retained for 15 minutes, up to 50 entries. The docked and mini layouts have clocks and steady text dots on running rows; desktop has clocks and steady SVG image dots. The timeline is computed once per draw and advances in 15-second steps. A run shorter than one step still draws one step wide. Inactive timers pause. The panel has no configuration.

The tracking hooks only watch and pass events on unchanged. Native records, main-session readings and the folded groups are saved in session state through queues that keep only the latest pending snapshot. The panel shows one toast per session the first time saving the panel state (agents, session or folded groups) fails; jobs keep their own warning. See [Privacy and permissions](../../docs/PRIVACY.md#pantheon) for the stored fields and tool-input redaction.

## Above-prompt strip

Since 0.13.0 pantheon draws an always-on strip above the prompt, absorbed from the former hud plugin:

A rounded box in flightdeck's mini style, at most four rows, kept next to the prompt:

- Session row: model and effort, working or idle, the context as a gauge with its percentage, the prompt cache with time left and hit share (red with what to rewrite when expired), the session cost, folder and branch, changed lines, and `⚡fast` while fast mode is on.
- 5h and 7d rows, drawn as hud drew them and lined up column for column: a 10-cell bar with a `│` clock mark (`━` used, `╌` slack, `─` rest), the percentage, the `▲`/`▼` pace mark in points (amber `▲` ahead of the clock, red past 15 points or from 90% used, green `▼` behind) and the time left, then a projection: `at this pace: 100% in 1h40` when the window would run out before its reset, `at this pace: ~68% at reset` otherwise, and `at recent pace: 100% in 24m ↯` when the last 30 minutes climb at more than 1.5 times the window's average rate (the projection then uses that recent rate). Narrow terminals give up the projection first, then the bars, then the time left.
- Last row: the last turn's duration, agents spawned, edits, errors and its cost (`last turn 2m37s · 2 agents · 4 edits · 0 errors · +$0.18`). The `+$` is the change in the session cost during the turn, so it includes what background agents spent in that time, and the agents counted are those the main loop spawned, Workflow ones included; while subagents run it shows them instead, a pulse (green, red on failure), the role and a clock each, with "+N" for the rest.

Options (`/plugin`): **Above-prompt strip** (`abovePrompt`, on by default; turn it off to hide the strip) and **Pace start** (`paceStart`, points of lead over the clock that still count as on pace, 0 by default). The suggested next prompts hud offered have no replacement. See [Privacy and permissions](../../docs/PRIVACY.md) for what the strip reads.

flightdeck users: `/plugin uninstall flightdeck`. If hud is still installed, both strips show above the prompt; remove it with `/plugin uninstall hud`.

## Edit gate

The plugin option `gate` is off by default. When enabled, it checks the main session's `Edit`, `Write` and `NotebookEdit` calls; subagents always pass through. Local size and path rules decide, with no network request and no API key.

The rules allow a single-file change of at most 5 changed lines and a documentation change (`.md`, `.mdx`, `.txt`, `.rst`) of at most 20. They deny a change to more than 3 files or of more than 100 lines, with a message pointing to developer for code (and to ux for visual work). For a `Write`, whose removed lines are unknown, the added lines count as a lower bound. Workflow, migration, manifest and lockfile paths, unknown line counts and everything else in between ask: in interactive sessions with a surface the call is held for **Proceed** or **Cancel**, and without one it is denied immediately with “Pantheon edit gate requires an interactive session to confirm this edit. Edit denied.” Disabled roles are replaced with a request for the person to handle the work.

An unexpected exception during evaluation holds the edit in an interactive session with the fixed message “Ask the person before proceeding by rules. Please ask the person to handle implementation; the main session should not edit it itself.” Without an interactive surface, recovery denies immediately. If the hold itself fails or is interrupted, the edit is denied rather than run without a decision. Once the call is forwarded, a rejection propagates to the engine without opening another confirmation or executing the tool again.

Exempt paths are `<repo>/.pantheon/plans/**`, `~/.claude/plans/**`, `~/.claude/projects/*/memory/**` and the session scratchpad (`<tmp>/claude-<uid>/*/*/scratchpad/**`, for the current user). `<repo>/.pantheon/flow/**` holds the flow's approval and state: it is not exempt, and an edit to it always asks. Paths are resolved through filesystem links before exemptions are checked. Everything else under `~/.claude` is gated.

The gate judges one tool call at a time: a large refactor made of many small edits can pass call by call. A per-turn accumulator is deliberately out of scope for this version. Bash writes are not gated.

## Flow

A plan written with the planning skill carries a fenced `pantheon-flow` block: the goal, the tasks (`files` each may write, `acceptance` checks as argv commands and/or semantic `criteria`, `role` developer or ux, `risk`, `dependsOn`, `sideEffect`) and the limits. The flow controller holds the session to it: a task is done when its checks pass and, where the plan asks for them, an architect review (`risk`) and a QA verdict (`criteria`) say so.

- **Approve first, in two steps.** `/pantheon flow approve [plan path]` approves nothing and records nothing: it prints every command that would run on this machine (argv, directory and timeout, marked NEW or CHANGED against the plan you approved before), the files each task may write, and a 12-character hash of the block. You read it, then confirm with `/pantheon flow approve [plan path] <hash>`, which approves only if the block still has that hash. Without a path it uses the plan in force (never "the newest file"); a first approval needs the path. Approving the plan approves its checks: they run as commands (an argv, no shell, whose first element cannot start with `-` or contain `=`; from the repository root or the check's relative `cwd`; limited by `timeoutSec`). Only `OPENROUTER_API_KEY` and `TYPESAFE_API_KEY` are removed from a check's environment; it inherits the rest. Approval is refused while a role the plan needs (developer, ux, the architect for `risk`, qa for `criteria`) is disabled. `approve`, `pause`, `resume` and `stop` only run when you typed them (or your remote client or SDK host sent them): a scheduled prompt, another session's message, a channel or a plugin is refused, so the model cannot approve a block it wrote. A plan nobody approved is never enforced and none of its commands run.
- **Editing the plan.** Editing the block never switches enforcement off. The controller keeps running the plan as you approved it (a snapshot in `.pantheon/flow/<plan>/approved.json`), and adopts an edit by itself only when it is purely additive, which it journals and tells the lead: new tasks at the end of the list with `dependsOn` written out, no `onFail` and no `sideEffect`, an id the plan never used, files that overlap no task that is not done (nor a finished `risk` task, nor finished work unless the new task is `risk`), no dependency on an active task, and checks that are commands a regular task of the plan already approved (same argv and `cwd`, timeout not above; not an `onFail` branch's or a side effect's command); extra `criteria`, or extra checks that are an approved command, on a task that has not started; and `risk` raised. Anything else (the goal, a role, `files`, `dependsOn`, `onFail`, `loop`, `sideEffect`, the limits, the plan id, a removal, a new command, a longer timeout, a changed `cwd`) waits for `/pantheon flow approve`, which replaces the snapshot with the block as it is now; `/pantheon flow status` lists what is waiting and why. An edit that mixes additive and other changes waits as a whole, and a plan file that does not validate changes nothing. A plan is bounded (100 tasks, 50 files, 20 checks and 20 criteria per task, 64 words per argv, a 256 KB block) and no task may list files under `.pantheon`, `.git` or `.claude`. Same argv is not the same code: a check that runs a repository script trusts that script, as an approved check does.
- **The approval is not a file.** Every file under `.pantheon/flow/` can be written by an edit, so none of them is believed on its own: `/pantheon flow approve` (and an adoption) leaves a record in the plugin's own store, and a snapshot counts only while it is exactly the flow that record names. The plan in force is also what that store names, so deleting or redirecting `.pantheon/flow/active` changes nothing. A snapshot that is missing, edited or unattested is never run and never forgotten: the flow keeps its approval, `/pantheon flow status` says "NOT trusted", and in `enforce` a Stop is held once per prompt of yours, with "the approved snapshot changed outside /pantheon flow approve ... read the commands it lists, then confirm with the hash". Put the file back as it was and enforcement resumes. Plans approved before this version have no record: approve them once more after upgrading.
- **Where the record lives.** The store is a JSON file under your Claude Code configuration directory (`~/.claude/plugins/store/pantheon_<install source>-<hash>.json`): outside the repository, and not writable by other plugins or hooks through the plugin API. It is still a file your account can write, so a Bash call or a Write tool call to that path can reach it unless you deny it: add the permission rules `Edit(~/.claude/plugins/store/**)` and a Bash rule for the same path (and keep `gate` on if you want the main session's edits gated; Bash is never gated). Agents the flow links to a task are refused that directory. The file's name carries how the plugin was installed: loading it with `--plugin-dir` and from a marketplace are two stores, so approvals read as unattested and need `/pantheon flow approve` again. A forged `state.json` can still mark the flow done, paused or stopped (it cannot add a command that runs).
- **Mode.** The plugin option `flow` is `off`, `shadow` (the default) or `enforce`. `off` does nothing and writes no file. `shadow` decides exactly as `enforce` does, but only journals what `enforce` would have done: it blocks, denies, attaches and rewrites nothing. `enforce` does the following.
- **Delegations.** A task is delegated by starting the Agent description with `[<taskId>]`. The delegation must go to the task's role; `qa` and `architect` can be given a `[T]` task only while it awaits their receipt (the architect also to diagnose a task that ran out of attempts), and a `[T]` delegation cannot set `isolation`; otherwise the spawn is denied. In `enforce`, a QA agent's brief ends with the approved plan's criteria for the task, numbered as it must answer them, so the lead's own words cannot hand it the answers (`shadow` leaves the brief as the lead wrote it).
- **Write ownership.** A developer or ux agent linked to a task cannot `Edit`, `Write` or `NotebookEdit` outside the task's `files`, and neither can any subagent it spawns (they inherit the task, and their denials count for the task's agent). Paths and the repository root are resolved through links first, so a link out of an owned file leads outside and `/var` against `/private/var` does not matter; a path the host cannot resolve is refused. Only this session's scratchpad is also allowed. When the check cannot finish in time, `enforce` refuses a write by an agent the flow linked to a task (it can be tried again) rather than let it through unchecked. A denied write also counts as a failed attempt at the task's end. A main-session edit to a file of a task that awaits a receipt clears the receipts it had earned and moves the task's delivery on, so a review already running is ignored; the task keeps waiting for a new review, and the lead is told in the result of the edit (the path is placed by the host's real paths, as write ownership does).
- **Git.** The shell commands of `Bash` and `Monitor` that run `git`, `gh` or `glab` are held to who runs them, with or without a plan: the gate follows the mode and needs no flow. It is a guardrail that reads the text of a command, not a security boundary: your own deny rules and the server's branch protection are the boundary.
  - **The lead** reads and pushes, and never pushes to `main`, `master`, `develop`, `release` or `release/*`. A push that does not write `<src>:<dst>` for every refspec (`git push`, `git push origin`, `git push origin feature`, `git push origin HEAD`) leaves the destination to git, which the push settings can change, so it is held to the push settings (`remote.*.push`, `remote.*.mirror`, `push.default` of `upstream`, `tracking` or `matching`) and, when it names no branch, to the checked-out branch, looked up with `git rev-parse --abbrev-ref HEAD` where the command runs. A detached HEAD, a failing `git`, a `cd`, `--git-dir` or branch change on the same line that is not joined by `&&`, an agent that works in a worktree of its own, or a destination that is a variable or a substitution makes it unknown, and unknown is denied. Write `git push origin <src>:<dst>` to push without a lookup. Forced, deleting, mirroring, `--all`, hook-skipping and `merge_request.*` pushes are denied too. Everything else that changes state (add, commit, reset, rebase, merge, checkout, switch, stash, worktree) and PR/MR work goes to the `git` role; with that role disabled the lead does what it does, under its limits.
  - **A task's developer or ux** commits its own task: `git add -- <paths>` and `git commit -m "<type>(<scope>): <summary> [<taskId>]" -- <paths>`, with explicit files the task owns (resolved by the host as write ownership is) and the task id in `-m`. `-A`, `.`, `--amend`, `--no-verify`, an AI attribution, and anything else that changes state are denied. A developer or ux that no task links keeps the same verbs and flags, with every path its own.
  - **The `git` role** keeps checkout, switch, worktree, stash, squash and PR/MR. It does not push or merge, never names a protected branch in `branch -d|-D|-m|-M|-f`, `update-ref`, `tag -d|-f` or a branch it creates (`checkout -b|-B`, `switch -c|-C`, `worktree add -b|-B`), never writes a push, remote, `url.*`, include or program setting with `git config`, never changes branches, refs, merges or files through `gh api` or `glab api`, and its commit, merge, rebase, reset, cherry-pick, revert, am and pull are denied on a protected or unknown current branch.
  - **Every actor** is denied a hidden git (`eval`, `bash -c "$x"`, a variable for the verb, `xargs`, `ssh`, an alias, a pipe into a shell, or a command that runs another such as `op run -- git push`), `-c` and `--config-env` outside `color.*`, `core.quotepath`, `advice.*`, `i18n.*`, `user.name` and `user.email`, environment that skips hooks or runs a program (`GIT_DIR`, `GIT_CONFIG*`, `GIT_SSH*`, `GIT_PAGER`, `PAGER`, `EDITOR`, `HOME`, hook-skip variables), `ext::` and `fd::` URLs, `--upload-pack`, `--receive-pack` and `--exec` on push, fetch and clone, and `gh alias set|import` and `gh extension install`. A `gh` or `glab` group Pantheon does not know is held as state-changing. The read-only roles (code-reader, docs-reader, architect, qa, council seats) may only read; any other agent (general-purpose, Explore) gets the lead's rules.
  - **Journal.** `shadow` records each refusal in the active plan's journal (`git_gate`, with the actor, the task and the git commands of the line without their arguments, `wouldBe: block`, secrets redacted) and denies nothing; with no active plan it records nothing. Not covered: a script written and then run (`./push.sh`, `make`, `npm run`, `python -c`, `curl` to the forge API), a direct edit of `.git/config`, `--recurse-submodules=on-demand`, `git fetch origin x:main` and `gh workflow run`.
- **Task end.** When the agent returns (the Agent tool result in the main loop, or the background task's notification, which is read only from its envelope: it needs a `<task-id>` and a `<status>` before the `<result>`, and only `completed` counts), the task's checks run and the controller's verdict, such as the next task or the failure to retry with the output, is appended for the lead to read. A QA verdict is read from `C<n>: pass|fail — <evidence>` lines plus a final `QA: pass|fail|blocked`; a partial pass is a fail, `blocked` pauses and asks you, and an unreadable answer is no receipt. The architect ends a review with `REVIEW: pass|fail`. A QA verdict is void when the content of the task's files (as they are in the working tree, tracked or not, deleted ones included) changed while QA ran; an unrelated commit, QA's own artifacts, or a commit of those very files with the same content do not void it.
- **Stop.** On the main session's Stop the checks of the active tasks, the tasks awaiting a receipt and the done tasks (a regression) run; a failing check, a task still open or a missing receipt holds the stop with the reason and the failing output. A pass is kept per tree snapshot (HEAD, `git diff HEAD` and the untracked files, outside `.pantheon/`): a Stop on a tree that did not change, and that the checks themselves did not change, runs nothing again; a fail, a timeout or a command that could not run is never remembered and runs again. The evaluation has a deadline of 120 s that covers its git calls too: a check that does not get to run in time is unverified, which is never a fail and never costs an attempt, and in `enforce` the lead is told which task in progress has checks that never ran. A command the host cannot run at all is not blamed on the task: the flow allows, says so and journals `check_unrunnable`. It never blocks while agents or workflows are pending in the background (a dev server or a monitor is not waited for), never more than `maxBlocks` times (at most 7, one short of the engine's 8) between your prompts, and pauses when the same failure repeats three times. Your next prompt refills the budget and brings the goal, the current task and the last instruction back as context (the system prompt never changes).
- **Judge (optional, off by default).** At the end of a task the agent's own report can be checked by an outside judge, Jev, over OpenRouter (or TypeSafe directly). The judge informs and the flow decides: it can never mark a task done or let one through, only make the next decision stricter. Where the checks pass and the task would be done, it asks whether the report really says the goal was made, names remaining work or an unresolved problem, or speaks to its evaluator; if it doubts, the task waits for a QA verdict, even without criteria. Where a check fails and attempts are left, it asks whether the agent gave up, blames something outside the task, or fails the same way again; if so, the task goes to the architect's diagnosis now instead of burning another retry (it never skips an `onFail` branch, a pause or the person). Options: `judge` (`off`; `shadow`, which asks and journals what it would have done and changes nothing; `escalate`, which acts, and only in `enforce` mode on an approved plan: in `shadow` mode it only journals), `judgeKey`, `judgeRoute` (`openrouter`, the default, or `typesafe`) and `judgeBaseUrl` (optional, https only).
  - **What is sent**, and only while `judge` is `shadow` or `escalate`, a key is set and the plan is approved, at a task end or a retry: the task's goal as the approved plan states it (for a task adopted from a plan edit, as the lead wrote it); the last 2000 characters of the agent's final message; and, on a retry, the last 1500 characters of the first failing check's output and of the previous failing output. Before sending, only secrets in common shapes (keys, tokens, passwords, credentials in URLs), email addresses and file paths (your home becomes `~`, the repository root is dropped, any other absolute path becomes `<path>`) are removed. That is all the redaction does: code, diffs, commands and file excerpts that the message or the output quotes go as written, so do not turn the judge on for a repository whose agents' reports or test output you would not send to the judge's host. The request goes to `openrouter.ai` (`api.typesafe.ai` with `judgeRoute` `typesafe`, or your `judgeBaseUrl`). The plan itself, other tasks, file contents and the lead's messages are not sent as such. With `judge` off nothing is sent and none of the settings below are read; with it on but no key, nothing is sent and they are not read either.
  - **The key** comes from the plugin's own options (it is stored as a secret) and from nowhere else: not from `<repo>/.claude/pantheon.json`, not from a file in the repository, not from the environment. A repository's own settings files (`.claude/settings.json`, `.claude/settings.local.json`) can carry plugin options that outrank yours, so, once a key is set, the plugin reads each settings source (user, project, local, flag and policy; the engine hands over each whole, `env` included, and only this plugin's `pluginConfigs` entry is looked at) to tell which options are yours: an option that the repository carries is replaced by your own value for it, or unset, with a toast naming the option (never its value), and when a source cannot be read the judge is off for the session. The key goes in the `Authorization` header to the route's host (or your `judgeBaseUrl`) and nowhere else: not in the body, the journal, the state, a toast or an error, and no `HTTP-Referer` or `X-Title` is sent.
  - **When it fails** the decision is the one the policy made without it. One request per delivery, 3 seconds at most, one retry on a 408, 429 or 5xx; a refused key or endpoint (401, 402, 403, 404) turns the judge off for the session with one toast; a rejected request (400, 422) stops that question set for the session; three failures in a row pause it for five minutes.
  - **Journal and state.** Each judged checkpoint is an `escalation` entry in `journal.jsonl` with the checkpoint, the mode, the model asked for and the one that answered, the request id and usage, a hash of the question set, the answers as returned, the thresholds used (provisional until calibrated), what they escalated to, what the second decision would be and whether it was applied. A failed call is journaled with its reason (and, for a rejection, only the status and the provider's error code). While the judge is on, `state.json` also keeps each failing task's last check output (redacted as above, up to 1500 characters) for the next retry's "same failure" question; it is dropped when the task is done or the judge is turned off. `/pantheon flow status` shows the judge's mode and whether it is off or paused.
- **Commands.** `/pantheon flow status` shows the mode, the plan, whether it is approved (and whether edits were adopted over the approval, or are waiting for it, with their reasons), each task's status and awaiting receipts, the budget, the judge and the last decision. `pause`, `resume` (it also clears a stop, starts the attempts over and gives the running agents' links the plan's files as they are now) and `stop` are yours; they also work in `shadow`.
- **State and privacy.** Everything stays on this machine, under `.pantheon/flow/`, except what the judge is sent (see Judge; it is off by default): `active` and `active.json` (the plan in force and the id it was approved under), and per plan `state.json`, `approved.json` (the flow in force), `journal.jsonl` (decisions with pass/fail per check, and reasons clipped to 600 characters that can quote failing output) and `side-effects.jsonl` (a done `sideEffect` task is never run again, even if the state is lost). The controller makes no network request and reads no key unless you turn the judge on and set a key (see Judge); then the journal also keeps each judged checkpoint, and `state.json` the last failing check output of a task (redacted) for the next retry.
- **Fail open.** Any internal error (a corrupt state file, a failing file system, a runner that rejects) allows what was asked, and `enforce` says so once with a toast; a state file that fails validation is journaled before a fresh one replaces it, and the flow then waits for a new approval. A check that timed out or whose command was not found counts as not passed, with why. A host store that cannot be read is not an error to fail open on: it attests nothing.

## Configuration

Layers apply in order: built-in defaults, `~/.claude/pantheon.json`, then `<repo>/.claude/pantheon.json`, merged field by field. Each file holds only what changes. For example:

```json
{
  "agents": {
    "developer": { "model": "opus", "effort": "high", "prompt": "..." },
    "code-reader": { "model": "sonnet" }
  },
  "council": { "seats": { "gamma": { "model": "fable" } } },
  "disabledAgents": ["ux"]
}
```

- `agents.<role>` and `council.seats.<seat>` accept `model`, `effort` and `prompt` (appended to the role's prompt). A new seat may leave out `model` to inherit the session's.
- Models must be Claude models: the aliases `opus`, `sonnet`, `haiku`, `fable`, `opusplan`, `default` and `inherit` (optionally with a bracket suffix such as `[1m]`), or an ID containing `claude`. Effort is not validated.
- `disabledAgents` takes role names, `councillor:<seat>` and `"council"`, combined as a union across layers.
- An invalid config shows a toast and the native agents stay as in the last valid config (or the defaults). The config is read again on every turn; no reload needed.

`/pantheon config` shows the effective configuration and field origins.

### Migrating to 0.17

Pantheon now runs only native Claude subagents: Codex, the `delegate`, `delegate_result` and `delegate_cancel` tools, `/pantheon cancel` and profiles are gone. A config that still uses them fails to load with a message saying what to do:

- `profile` and `profiles`: move each role's `model` and `effort` from `profiles.<name>.agents.<role>` to `agents.<role>` (and seats to `council.seats.<seat>`), then delete both fields. Clear the old **Active profile** value in `/config` if you set one.
- `sandboxCap`, `noNetwork`, `foregroundMinutes`, and `engine` or `sandbox` in a role or seat: delete them.
- Role renames: `explorer` is now `code-reader`, `librarian` is `docs-reader`, `executor` is `developer`, `designer` is `ux` and `oracle` is `architect`; `git` and the council seats keep their names, and the main session is labeled `lead` in the panel. Rename the keys under `agents` and the entries in `disabledAgents`; the native agents are now `pantheon:<new name>`. A config that still uses old names fails to load with one message listing every old name found in the file (in `agents` and in `disabledAgents`) with its new name (for example ``role `executor` was renamed to `developer`; use `agents.developer` ``), and there is no alias. Until the file is fixed Pantheon keeps the last valid configuration, which is the defaults at startup: disabled roles come back and your overrides are ignored, and it shows a toast with the error.
- Routing: `developer` writes all code, UI code and logic included; `ux` owns look and feel and implements it, and keeps the design criteria of the old designer. The split is by kind of work, not by file extension. `developer` and `ux` commit their own task; the lead pushes; `git` keeps squash, PR/MR, checkout, switch, worktree and stash.

### Migrating to 0.15

The `fixer` role became `executor` in 0.15 and is `developer` since 0.17. Rename `agents.fixer` to `agents.developer` and replace `fixer` with `developer` in `disabledAgents`. Configs that still use `fixer` fail to load with a message naming `developer`; there is no alias.

## Council

Ask for a council ("run a council", "second opinion", "quero consenso", "segunda opinião", "conselho") and the lead gets Council Mode: it dispatches every active seat in the background in the same turn, collects each answer as it arrives and synthesizes under `## Council Response`, `## Per-Councillor Details` and `## Council Summary`. Only prompts you type (terminal or Remote Control) trigger it, never quoted code, slash commands or SDK prompts.

## Skills

Four skills carry the workflow, and the lead invokes them itself when their description applies. They replace the superpowers integration, so the superpowers plugin is not needed.

| Skill | Use |
| --- | --- |
| `brainstorm` | Before creative or multi-step work: explores two or three approaches with you, reads code and docs through the code-reader and docs-reader, opens a worktree with `EnterWorktree` and writes the plan with a `pantheon-flow` block; you approve it with `/pantheon flow approve`. |
| `execute` | Carries out the plan: briefs developer or ux from the task, tags each delegation of an approved flow with `[<taskId>]` and follows the controller's verdicts, the implementer commits its own task, QA verifies criteria and the architect reviews `risk` tasks. |
| `debug` | On a bug or failing test: reproduce, form hypotheses, confirm the cause, then fix. |
| `finish` | Before claiming work is done: needs `/pantheon flow status` complete, runs the real validation, one architect review of the branch, then you push and `git` opens the PR/MR. |

- The plan lives in `.pantheon/plans/YYYY-MM-DD-<topic>.md`. `brainstorm` adds `.pantheon/` to the repository's `info/exclude`, so it is never committed and goes away with the worktree.
- The plan's `pantheon-flow` block lists each task's id, goal, files (write ownership), role (`developer` or `ux`), `dependsOn`, acceptance (checks as argv arrays and/or criteria), `risk` and `sideEffect`, and optionally `onFail` and `loop`. Tasks run in sequence unless their `dependsOn` are explicit and their files are disjoint; code-reader and docs-reader lanes always run in parallel.
- With an approved flow the lead follows what the controller says when a task returns (see Task end): start the next task it names, send the failing output to the same implementer, ask the architect to diagnose, ask `qa` or the architect for a receipt it says is due, or stop and tell you when it pauses. QA ends with `C<n>: pass|fail — <evidence>` per criterion and a final `QA: pass|fail|blocked`; the architect ends with `REVIEW: pass|fail`.
- A failing task goes back to the same implementer with the failing output up to `limits.maxAttempts` times (2 by default, so one retry); at the limit the architect diagnoses it (or its `onFail` task takes over), and one more failure is handed to you. An architect gate is one review plus at most two re-reviews.
- The worktree starts from `origin/<default branch>` unless `worktree.baseRef` is `head`.

## Security

Agents follow the session's permission mode and inherit its tools, MCP servers included, and that includes MCP tools that write. The architect, qa and council seats have Edit, Write and NotebookEdit withheld (qa writes only in the scratchpad, through Bash). The read-only roles (code-reader, docs-reader, architect, qa and council seats) also have the Agent tool withheld. Code-reader and docs-reader keep Edit and Write, and their prompts tell them not to change files, git or external state through Bash. The docs-reader may read a logged-in page through a `terminal-browser` the lead names, read only: no login, credentials, form submissions or clicks that change data, and it releases the browser when done. Developer, ux and git may write within their assigned scope. Git has the Agent tool withheld. Developer and ux keep it; their prompts forbid sub-delegation, without separate enforcement.
