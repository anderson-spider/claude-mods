# pantheon

Makes the main session the lead in the style of oh-my-opencode-slim. The six roles and every council seat are native Claude subagents; the configuration chooses each one's model, effort and extra prompt.

IMPORTANT: prompts and panel modules include third-party work. Keep `LICENSE` and the credits and full license text in `NOTICE`.

## Roles

- Roles and seats are registered as native `pantheon:<role>` or `pantheon:councillor-<seat>` agents with `$.agent.register` (no tool list, so they inherit the session's tools; architect, qa and councillors get `disallowedTools` Edit, Write and NotebookEdit; code-reader, docs-reader, architect, qa and councillors also get Agent; developer and ux get none), and hidden by an `agent.offer` guard when disabled.
- Developer writes all code (UI code and logic included) and runs scripts, test batteries and API calls within the brief, returning short results; no external research or sub-delegation. It tells the lead when a task is look and feel (guidance, not a refusal). Developer and ux commit their own task's files after the checks pass (`git add -- <paths>`, `git commit -m "<type>(<scope>): <summary> [<taskId>]" -- <paths>`; never `-A`, `.`, `--no-verify` or `--amend`, no AI attribution, retry once on `index.lock`) and never push, rebase, reset, merge, switch or stash; the lead pushes.
- UX owns look and feel (layout, hierarchy, color, spacing, motion, UI copy), makes mockups and throwaway prototypes (scratchpad, never committed) when the direction is open, and implements the chosen one, keeping the design criteria of the former designer; the split with developer is by kind of work, not by file extension. Docs-reader reads external docs and research; it does not write docs. Architect covers architecture, debugging, review and simplification. QA runs what was built and returns `C<n>: pass|fail — <evidence>` per acceptance criterion plus a final `QA: pass|fail` (partial coverage is a fail); it never fixes code or runs side effects and writes only in the session scratchpad through Bash.
- Developer and ux may write within their assigned scope. The lead decides the included changes and owns validation, and commits its own work. It also pushes, squashes and opens PRs/MRs itself, following the project's rules; there is no git agent and no gate over git commands. Its fixed push refusals are a force push without `--force-with-lease`, remote branch deletion, `--mirror`, and any push to main, master, develop, release or release/*.

## Config

- `config.ts` merges built-in defaults, `~/.claude/pantheon.json` and `<repo>/.claude/pantheon.json` field by field: `agents.<role>` and `council.seats.<seat>` take `model`, `effort` and `prompt`; `disabledAgents` is a union. The council has exactly two seats, `alpha` and `beta` (the keys of `DEFAULT_CONFIG.council.seats`): a config naming any other seat under `council.seats`, or `councillor:<seat>` in `disabledAgents`, fails to load with the "unknown seat" or "is not a seat" message, so no third seat is ever registered. Models must be Claude models (`models.ts`).
- Fields of the Codex and profile era (`profile`, `profiles`, `sandboxCap`, `noNetwork`, `foregroundMinutes`, an entry's `engine` or `sandbox`) the old role names (`explorer`, `librarian`, `executor`, `designer`, `oracle`, `fixer`) and the removed `git` role fail to load with one message listing them saying what to do.

## Edit gate

- `decisions.ts` is pure and holds the local size and path rules (`rulesVerdict`); `gate.ts` is pure and builds edit context, exemptions and messages. Pure modules never touch `$`; `register.tsx` owns host access, path resolution and the Proceed/Cancel hold. The gate makes no network request and reads no API key: with metadata only, "is this edit trivial?" is a code decision.
- The `tool.call` hook matches `Edit`, `Write` and `NotebookEdit`, main session only. It is registered after the tracking handler, which wraps it and observes the settled result once: held calls are not counted early and denials do not count as successful edits.
- Plugin option: `gate` defaults to false. Rules: a sensitive path (workflow, migration, manifest, lockfile) always asks; more than 3 files, or more than 100 lines (the known added plus removed lines, a lower bound when a Write leaves the removed count unknown), denies; a single-file change of at most 5 lines, or a doc change of at most 20, allows; unknown counts and everything else ask. An ask holds the call for Proceed/Cancel only when `session.start` reports `isInteractive: true` and a non-null `surface`, otherwise it denies without a hold. Recovery covers evaluation only; forwarding failures propagate to the engine without a second confirmation.
- Exemptions are `<repo>/.pantheon/plans/**` (`.pantheon/flow/**`, which holds the approval and the state the flow trusts, is not exempt and always asks), `~/.claude/plans/**`, `~/.claude/projects/*/memory/**` and the current user's session scratchpad; the rest of `~/.claude` is gated. Decisions are per call, with no per-turn accumulator or Bash write detection.

## Tracking and state

- `tracking.ts` holds pure reducers for native subagents and the main session, plus tool-input redaction.
- The tracking hooks (`turn.start`, `turn.step`, `turn.complete`, `session.measure`, `agent.spawn`, `tool.call`) only watch and pass events on unchanged.
- `pantheon.natives`, `pantheon.session` (with the ledger cost) and `pantheon.view` (the folded groups) live in `$.state`, written through queues that keep only the latest pending snapshot.
- The panel shows one toast per session the first time saving the panel state (agents, session or folded groups) fails.
- `register.tsx` builds host closures in each hook because `$` cannot be stored.

## Flow

The decision flow is wired by `register.tsx` over pure modules in `hooks/flow/`: `plan.ts` (the contract), `policy.ts` (the reducer), `store.ts` (files), `checks.ts` (approved checks through an injected runner, passes with a memo and a deadline), `verdicts.ts` (QA `C<n>:` lines and `QA:`, the architect's `REVIEW:`) and `controller.ts` (orchestration). The judge (T9w: the task end and the retry, in a flow) sits over `judge.ts` (the client and its breaker), `questions.ts` (every question, battery, threshold and the state builders), `redact.ts`, `escalate.ts` (what the numbers mean) and `judging.ts` (the options, the session's off switches and the `ask` the controller reaches it through); see the Judge bullet. The done check outside a flow and the model fit at spawn are T9c and not wired.

- `controller.ts` takes a `Ctx` with injected `fs` (read returns undefined only when missing), `run`, `now`, `root`, `mode`, enabled roles, `list`, `serial(planId)` and the check `memo`, and never touches `$`. Its entry points are `stopFlow`, `taskEnded`, `reviewed`, `inspectSpawn`, `inspectIsolation`, `inspectForcedBackground`, `mainEdit`, `humanPrompt`, `noteOwnership`, `noteDelivery`, `noteDeliveryDiagnostic`, `flowTaskFiles` and the commands (`approvePlan`, `controlFlow`, `flowStatus`). Each one finds the plan through `.pantheon/flow/active`, finds the flow in force (below), loads or creates the state (ledger applied, a changed flow rebased and `withMode`), settles the plan file's edit, runs `decide` then `applyMode`, saves and journals.
- Writes to a plan's files are one `createSerial()` job (`transact`: load, decide, ledger, save, journal). Long work (the checks and the git reads) runs before the job, because a hook waiting for the queue spends its own 10 s budget. Checks run only for the flow in force. A decision made on check results is dropped (`transactAt`) when an approval or an adoption moved the flow in force while the checks ran: results of another command must never settle a task. Every entry point is wrapped by `guarded`: an error warns, journals when the plan is known and answers allow (fail open); `off` returns before anything is read.
- Checks run as `env -u OPENROUTER_API_KEY -u TYPESAFE_API_KEY -- <argv>` (the host can only set variables, not unset them; `--` ends `env`'s options, which macOS and GNU `env` both accept, and `plan.ts` refuses an `argv[0]` that starts with `-` or contains `=`). Only those two judge keys are removed: the check inherits everything else. `passed: null` means the command timed out or `env` exited 126/127: a real failure with `couldNotRun` unset, so the Stop holds and a task end counts an attempt. A check that could not run carries `couldNotRun: true` instead: a `cwd` that is missing or not a directory (`Ctx.probeDir`, `$.fs.exists` and `$.fs.stat` in `register.tsx`, is asked first; the runner is not called) and the engine's own `failed to start: ENOENT|ENOTDIR|EACCES` (it names `env`, which is always found, so the command or the directory is what is not there). The policy reads those as unverified: no attempt is spent and a task end leaves the task where it is. At a Stop one counts only for a task with a delivery (`ends > 0`); an undelivered task is not finished and holds the Stop with `continue`. The Stop allows with `unverified`, naming them, only after the receipt step: tasks awaiting a receipt, active tasks and eligible required tasks still to start hold the Stop first. A `sideEffect` task whose only check could not run pauses with `ask_person` at task end (the effect may have run), is recorded in `sideEffectsDone` and is not offered for re-delegation. The other checks of the pass still run. Any other rejection of the runner throws `CheckUnrunnable`, which the controller answers with allow, a warning and a `check_unrunnable` journal note (with the task at a task end, none at a Stop), charging no attempt: it is for host failures that say nothing about the plan.
- A check pass (`createCheckPass`) reuses a pass while the tree snapshot is the one it was produced on (`treeSnapshot`: `git rev-parse HEAD`, a git-computed hash of `git diff HEAD` and of the untracked files' names and contents up to 300, never `.pantheon/`). Only a pass is remembered (a fail, a `null` or an unverified check runs again), and only when the snapshot after the pass equals the one before it: a check that changed the tree did not pass on the tree it leaves. A Stop derives its deadline from the targets: `min(600000, max(STOP_DEADLINE_MS, longest timeoutSec * 1000 + 30000))`, with a 120 s floor; `Ctx.stopDeadlineMs` overrides it. Snapshot git calls are inside it (each is cut to the time left). The longest timeout is used, not the sum, and the cap can cut a 600 s check. Stop decision entries store the observed evaluation time as `detail: 'elapsedMs=N'` for real-host diagnosis; host tolerance of long Stops remains unverified. After the deadline no check starts, the running one is cut to the time left and what did not run is unverified (no result, never a fail, no attempt) with a `checks_unverified` note; in enforce `StopOutcome.context` tells the lead which task in progress (active or awaiting) had checks that never ran, and the Stop hook returns it as `additionalContext`. The memo lives in memory, in `register`'s closure. The Stop's `check_failed` text for an active task whose attempts are spent and whose architect diagnosis is open (`diagnosisOpen` gives `decide` the ids as `diagnosis`) says what to do next: ask the architect with a description starting `[<id>]`, or `/pantheon flow resume` or `/pantheon flow stop`; with the architect disabled it is a pause with `role_unavailable` instead.
- Before the budget step takes over, `onStop` settles only tasks active and eligible at the start of its settlement step, named in `StopOptions.attempted`, with nonempty checks all present and passing, and no `sideEffect`. It calls `finishOrAwait` after failures and before receipts: the same Stop asks for missing receipts or completes the flow. A task already awaiting a receipt is skipped (step 6 asks for it, and its earned receipts stay); otherwise receipts are cleared first, as at a delivery, since the reviewer saw older code. It never increments `ends`. No attempted ids preserves the previous path, including the existing budget-time `settleByChecks`. `StopInput.workLinks` carries `{task, plan, end}`; `evaluateStop` filters the plan and compares `end` with `before.ends[task] ?? 0` inside `transactAt`. The new settlement requires known equal snapshots before and after checks, including with no memo or only cache hits. Passing attempted work also clears its previous failing output while the judge is on. Missing links or unknown/changed snapshots do not trigger this new path. Links are stored at spawn or recovered by the existing lookup; regressions do not increment `ends`, so a stored link can remain eligible across a regression. A late delivery is `not_active` while other work remains, `already_done` after flow completion.
- A QA snapshot is `treeSnapshot` limited to the task's `files`: the names git lists for them (`ls-files --cached --others`), the ones deleted and the content of each (`hash-object --stdin-paths`; past 2000 files, the diff). Only its digest is compared, so an unrelated commit, QA's own artifacts or a commit of those files with the same content do not void a receipt.
- Hooks in `register.tsx`: `agent.spawn` (matcher: a description starting `[`) links the agent id to its task in the `pantheon.flowAgents` state value (task, kind work|review|diagnosis, reviewer, end count at spawn, denials, files, QA snapshot, `root` for an inherited link; the newest 48) and enforces decisions 16 and 17; a `[T]` spawn with `background: true` is asked to run in the foreground (`inspectSpawn` with `background`: enforce rewrites `background: false` through `next` and journals `spawn_background`, shadow journals it and rewrites nothing), because the host gives no attributable end for a background agent; an agent definition with `background: true`, remote isolation or a teammate can still force background, and then the `tool.call` hook on `Agent` journals `spawn_background_forced` (`inspectForcedBackground`, both modes) and, in enforce, appends the context telling the lead to re-run it in the foreground; a `[T]` spawn that stores no link journals `spawn_unlinked` (`noteDelivery`, `event: 'delivery'`), and in enforce only appends the approved criteria to a QA agent's prompt (shadow rewrites nothing; a delegation with no plan in force links nothing and holds nobody back); a second `agent.spawn` hook (matcher: a `parentAgentId`) gives a subagent of a work agent the parent's task and files; `tool.call` on `Edit|Write|NotebookEdit` with an `agentId` enforces ownership from the link's files, with the path and root resolved by the host as the gate does and only this session's scratchpad exempt (the hook has a `.catch`: when it did not finish, `flowWriteFallback` refuses a write by a linked work agent in enforce); the unmatched `tool.call` hook (tracking) reports a main-session edit to `mainEdit` after the settled result (its `resolve` asks the host for the real root and path once a plan is in force) and appends its text to the result; `tool.call` on `Agent` refuses `isolation` on a `[T]` delegation, then appends the verdict as `context` of the result (a `[T]` delegation is foreground, so this is its task end); `prompt.submit` for origin `task-notification` attaches the verdict as context for an agent the flow linked (a `[T]` delegation never arrives this way, since it runs in the foreground) (`parseNotification` needs `<task-id>` and `<status>` in the envelope before `<result>`; the link is the stored one, or `adoptFlowAgent` by lookup when none is stored, and each discard is journaled as a `delivery` note: `delivery_unparsed`, `delivery_unlinked`, `delivery_adopted` (with `status=` when not `completed`), `delivery_ignored`; an id the host does not list as an agent gets only its shape note, and no delivery note carries the agent's output), and for `composer|bridge|sdk` it refills the budget and re-injects state; `classic.Stop` runs after `next(e)` (it leaves another hook's block alone), counts only `subagent` and `workflow` background tasks and returns `{ block }` only in enforce, and a `notice` in enforce for `budget`, `complete` and `unverified` (not in shadow). The engine refuses the same event twice without a matcher, so each of these has a distinct one. Hooks act only after `session.start` found the root: the flow never runs a command to look for it.
- Delivery diagnostics are recorded before notification parsing or Agent-result filters through `noteDeliveryDiagnostic`, the same guarded per-plan journal queue as `noteDelivery` (reason capped at 300). `envelope_shape` uses known envelope tag/field names, sanitized status at most 20 characters, id length, result presence and length buckets (`0`, `1-256`, `257-1024`, `1025-4096`, `4097+`), never body text, raw ids or arbitrary names. A per-runtime signature set reserves before awaiting and stops at 40; a signature that could not be written (no plan in force yet) is released, so the same shape is recorded once a flow is approved; a reload resets it. Counters keep growing after the cap: `notifications` and `agentResults` count arrivals, `parsed` counts recognized id/status pairs, `linked` counts flow links found, including events that cannot deliver. The main Stop writes `delivery_counts` before its decision only when counters changed. Seen without parsed suggests an envelope mismatch; parsed without linked suggests link loss. Monitor events have a shape and increment notifications without becoming deliveries.
- `$.state` reads inside a dispatch are snapshots, so the links are also kept in memory (`FlowRuntime.links`); an agent's first write finds a link not yet stored by waiting (up to 2 s) for the delegations in flight (`FlowRuntime.pending`), then by asking `$.agent.list()` (its `[T]` description or its `parentId`). Only the first level waits (one wait of at most 2 s, not one per level of parents); the lookup is `inspectSpawn` with `lookup`, which journals and refuses nothing. At Stop, stored links from the atom are merged with runtime links (runtime wins by agent id); only `work` links are projected into `workLinks`, with no lookup or adoption. Agents found to belong to no task are remembered; `/pantheon flow resume` forgets that, and refreshes the links' `files` from the approved plan.
- Approval and plan edits (decision 19). Nothing under `.pantheon/flow/` says what the person approved: any edit can write those files. The approval is the plugin's store (`Ctx.attest`, required, backed by `$.store` in `register.tsx`; contract `FlowAttest` in `types/index.d.ts`): `flow.attest.<sha256(real root)[:32]>.<planId>` holds `{ approvedHash, adoptedHash?, snapshotHash, adopted? }` and `flow.active.<same>` holds `{ planId, plan }`, the plan in force; the pointer files (`active`, `active.json`) only echo it, so deleting or redirecting them changes nothing (before the store held it, they are the fallback). The root is keyed by its real path (`$.fs.stat` with `resolve`), not the spelling of the cwd. Records are written only by `approvePlan` and by an adoption `amend` accepted, before anything else is written for them (record, then `approved.json`, state, `active.json`, pointer). A plan stands approved only while `approved.json` is valid, hashes to what the record says and is exactly what it names (`matchesAttest`); the state is progress and is brought back to that approval (a lost or forged state restarts its tasks from the approved flow). A store that rejects `get` is read as no record (`tampered`, never approved, never an error to fail open on), and so is one that cannot say which plan is in force (`get` of the active key rejects): the plan the pointer files lead to is held, no check runs, and the pointer files are not a fallback for it (with no pointer file either, a plan nobody can name is held, counted in memory, when `.pantheon/flow/` exists, which `flowKept` probes with `FlowFs.read`: anything but undefined is present; with no such directory it is `none`, since nothing was ever kept); one that rejects `set` makes an approval fail before anything is written, and an adoption is dropped (the edit waits with that reason, the flow in force goes on).
  - What the store is, and is not: a JSON file at `~/.claude/plugins/store/pantheon_<install source>-<hash>.json`, outside the repository and not writable through the plugin API by other plugins or hooks. A Bash call or a Write to that path reaches it, and the edit gate (off by default) never sees Bash: the boundary there is the person's own permission rules (`Edit(~/.claude/plugins/store/**)` and a Bash rule), and the ownership check refuses that directory to every linked task agent. The file name carries the install source: loading the plugin inline (`--plugin-dir`) and from a marketplace are two stores, so approvals read as unattested until approved again. Accepted residual risk, said plainly: `prepare` restores only `approvedHash` from the record, so a forged `state.json` can still mark the flow `done`, `paused` or `stopped`, mark tasks `done` and fabricate `receipts`, which skips the checks' wait and the QA or architect receipt on a criteria-only or risk task (it cannot add a command that runs, and a task with a check is still re-checked at the Stop); mirroring the progress in the record was judged not worth the writes.
  - Approval is two steps and only the person's own run counts. `/pantheon flow approve [path]` records nothing: it prints every command that would run (argv, directory, timeout; NEW or CHANGED against the attested plan, or all new when none stands) with each task's goal and the files it may write and a 12-hex confirmation of the block's hash. Every argv word, directory, goal and pattern is shown as a JSON string with the characters JSON leaves raw (DEL, C1, direction marks and overrides, line separators, the BOM) spelled `\uXXXX`, `validateFlow` refuses those characters (and every C0 control) in an argv word, a `cwd` and a file pattern, and the listing never truncates a command: `PLAN_LIMITS.totalChecks` (100 in all) bounds the plan so that the whole list fits, and `listingRefusal` makes `approve` refuse to hand out a confirmation for a plan with more (only the "no longer run" list and a long goal are shortened, since neither is something to approve); `/pantheon flow approve [path] <hash>` approves only when the block is the one that was listed. Twelve digits are what the person types and too few to bind a block (a birthday collision between a benign block and a malicious one is seconds of hashing), so the listing keeps the FULL hash in process memory (per root, plan id and plan file), and a confirmation needs that listing, the current block's whole hash equal to it and the typed digits to be its prefix (`confirmationVerdict`); one with no listing in this process (a restart, a reload) is refused with "list first", and an approval spends its listing. Without a path the plan in force is used, never "the newest file". `approve`, `pause`, `resume` and `stop` run only when `command.run`'s `origin.kind` is `composer`, `bridge` or `sdk`; a scheduled prompt, another session, a channel or a plugin is refused with a message (`status` stays open), before anything is read: with the flow off `status` answers "off" and the others answer off or refused with no repository lookup, no settings read and no store access. Engine limits, not the plugin's: `composer` cannot tell the person from another agent typing into the same pane (a multiplexer, a terminal driver), and `sdk` accepts whatever orchestrates the SDK host.
  - A plan that was approved but whose snapshot is missing, unreadable, edited or unattested, or whose state records an approval nothing attests (a state from before attestation, a cleared store: one `/pantheon flow approve` after upgrading) is `tampered`, never "unapproved": no check of it runs, the state keeps `approvedHash` (a lost approval would be a switch), the Stop is held once between two prompts in enforce ("the approved snapshot changed outside /pantheon flow approve ... read the commands it lists, then confirm with the hash"; then let through, a human prompt refills it and tells the lead again; pause, stop and background work are respected) and shadow journals `snapshot_tampered` once. Restoring the file as attested resumes enforcement without an approve.
  - An edit never switches enforcement off. `locate` compares the file with the flow in force; `prepare` runs `amend` (plan.ts, pure) through a per-process cache keyed by everything it reads, and adopts the edit only when it is purely additive (the allowlist is the comment above `amend`; any other change, or a part of an edit that is not additive, makes the whole edit wait): `rebase` onto the adopted flow keeps `approvedHash` and sets `adoptedHash`, the record and `approved.json` are rewritten, and a `kind: amendment` journal entry (`amendment_adopted`, with both hashes) is written. What waits is journaled once per content (`amendment_pending`, the reasons capped at 20; `state.seenEdits` is the bounded set of keys), shown by `/pantheon flow status` ("N waiting for /pantheon flow approve", with reasons) and in the reinjected context; a file that does not validate is journaled once per content (`amendment_invalid`) and changes nothing. The diff base is the flow in force, so adoptions chain; every id the plan has had (`state.seenIds`, bounded, seeded from the journal and the ledger once) is never reused. An adoption whose new work needs a disabled role waits, as approve would refuse it. Tasks adopted over the approval are listed in the record: status and the reinjection mark them as the lead's, not the person's.
  - `validateFlow` bounds a plan (`PLAN_LIMITS`: 100 tasks, 50 files, 20 checks and 20 criteria per task, 100 checks in all, 64 argv words, 300-character patterns with at most 8 wildcards, a 256 KB block) and refuses `files` whose first segment is `.pantheon`, `.git` or `.claude`, so no amendment can adopt them; `ownershipVerdict` never grants anything under `.pantheon` (the plans included: a task with `**/*.md` must not own the plan and have its own edit adopted without the lead), `.git` or `.claude` whatever the patterns match, and the edit gate does not exempt `.pantheon/flow/**` (only `.pantheon/plans/**`) and always asks for it. A new task may reuse only the commands of regular tasks (not an onFail branch's or a side effect's), and overlaps no task that is not done, nor a done `risk` task, nor a done task unless it is `risk` itself.
  - A decision made on results gathered for another flow than the one in force is dropped (`transactAt`) and the evaluation starts over once; changing again, the Stop is held once saying so (only in enforce, never while agents or background work run, and as a block like any other: it spends the budget, counts toward the engine's run of consecutive blocks and is let through when either is used up) and a task end or review asks to be repeated.
  - Receipts are voided by an edit of a file of a task awaiting them from the main session and from an agent no task links (a general-purpose subagent, a developer with no `[T]`: the tracking hook, `link.kind !== 'work'`); a work agent is held to its task's files by the ownership hook instead. `mainEdit` on the plan file itself returns the outcome for the lead in enforce (adopted, waiting with reasons, or invalid). `/pantheon flow approve` replaces the snapshot with the current block, keeps the progress of tasks still in it, and clears `adoptedHash` and what waited. Journal kind `escalation` is the judge's (see the Judge bullet).
- Shadow journals what enforce would do (`wouldBe`) and attaches, denies and blocks nothing. Plugin option `flow` (`off`, `shadow` default, `enforce`).
- `/pantheon flow status|approve [path]|pause|resume|stop` is handled in the `pantheon` `command.run` hook; `approve` writes the snapshot, the state and the pointer, and records the hash, and `resume` clears a pause or stop and the attempts of unfinished tasks.
- Judge (T9w; decisions 10, 11 and 18). The judge informs and code decides: it never marks a task done, never advances, never removes a gate, and its only reach is to make the next decision stricter. Plugin options: `judge` (`off`, the default; `shadow`; `escalate`), `judgeKey` (declared `sensitive`), `judgeRoute` (`openrouter`, the default, or `typesafe`) and `judgeBaseUrl` (optional).
  - Two passes, in `controller.ts`. A task end is decided without the judge (pass 1). `probe` then runs `decide` again with each escalation in turn and compares the results: only where `requireQa` (checks pass, the task is not `sideEffect`, QA is available and not already required) or `retryToArchitect` (a failing check with attempts left, no ownership denial, the architect available, no `onFail` branch still to run) would change the decision is the judge asked, with the one battery of that branch (`taskEnd`; `retry`, with `same_failure` only when `state.lastOutput` holds the previous failing output). Nothing else is ever sent: not a paused, stopped, done or unapproved flow, not a side-effect task, not a delivery with no agent message, not a Stop, review, regression or QA fail. `askJudge` runs before the plan's queue (a request is long work, and a hook waiting for the queue spends its own 10 s), once per delivery (`JudgeMemo` survives the second attempt of a flow that moved while its checks ran). Inside the job `stepJudged` decides from the state as it is then, uses the answer only if the decision is still on the branch that was asked about, computes `taskEndEscalation`/`retryEscalation` from the answers and runs pass 2, `decide` with `requireQa`/`retryToArchitect` as the second input, before `applyMode`. Pass 2 replaces pass 1 only when the judge mode is `escalate`, the flow mode is `enforce` and the plan is approved (`enforcing`); in `shadow` it is journaled as `would`, and the flow's own `shadow` mode then applies `applyMode` to pass 1 as for any decision. A judge that is off, switched off, breaker-open, timed out, failing or answering garbage gives pass 1 unchanged.
  - Policy (`policy.ts`). `requireQa` on a task with no criteria records it in `qaRequired` (sticky until done, as before) and, where the judge-less outcome is already a pause (a disabled architect on a risk task), leaves that pause; it is ignored (`note: 'require_qa_ignored'`) on a side-effect task or when QA is disabled, because the judge cannot pause a flow. `retryToArchitect` makes a failing delivery with attempts left a `failTask`/`architect` now: `attempts` becomes the limit (never lower than it was), so the ladder goes on as after the last attempt (one try after the diagnosis, then the person); it never overrides ownership, the limit, a pause or an `onFail` branch, and is set aside (`retry_to_architect_ignored`) when the architect is disabled or a branch is still to run. The two-pass property tests (`flow-policy.test.ts`) hold for every `decide`: never more tasks done, never fewer attempts, never a block or pause turned into an allow or advance, never a task started that pass 1 did not start (the event's own task may stay active), nothing paused, stopped or finished by the judge.
  - What is sent, from `checkpoint()` in `questions.ts` after `redact`: the task's goal (head, 2000 characters; as the approved block states it, which for a task adopted from a plan edit is the lead's wording), the agent's final message (tail, 2000), and on a retry the first failing check's output (tail, 1500) and the previous failing output (tail, 1500). `redact` removes secrets in common shapes, email addresses and file paths (the home becomes `~`, the root is dropped, any other absolute path becomes `<path>`) and nothing else (an unquoted `api_key => value`, and a value after any other unquoted separator it does not know, is not masked, by design): code, diffs, commands and file excerpts that the message or the output quotes go as written, so the user-facing text must never say otherwise. Not sent as such: the plan, other tasks, file contents, the lead's messages. Everything untrusted sits under `untrusted`; `addressed_to_judge` is asked with every battery and only ever hardens.
  - Where the key comes from. The plugin options and nothing else: never `<repo>/.claude/pantheon.json`, a file of the repository, an environment variable or a `$.fs` read of a dotfile (checks also run without `OPENROUTER_API_KEY`/`TYPESAFE_API_KEY` in their environment). The options are what the plugin API hands over after merging every settings source, and a repository's `.claude/settings.json` and `.claude/settings.local.json` can carry `pluginConfigs` that outrank the person's user settings, so `resolveJudge` (pure) attributes them: with a key set (without one nothing can be sent, and the settings are not read) `register.tsx` reads `$.settings.read` for `user`, `flag` and `policy` (the person's, in precedence order) and `project` and `local` (the repository's) and an option whose value a repository source carries (values compared as `String(v).trim()` on both sides, so one the API normalized cannot pass as the person's) is replaced by the person's own value for it (the highest-precedence of theirs) or unset, with one toast per class of problem naming the options, never the values (the options a repository set, together; a key missing, folded into the first when the repository's key was the one ignored; a base URL that cannot be used). The person's own `.claude/settings.local.json` is a repository source for this purpose: set the options in user settings. When any source cannot be read, or answers something that is not settings, nothing is attributable and the judge is off for the session (one toast). Only this plugin's `pluginConfigs` entries (`pantheon`, `pantheon@*`) are looked at, but the engine hands over each source whole, `env` and helper commands included: the privacy text says so. A repository that sets `judge` to `off` over the person's `shadow` keeps it off (that is the safe direction). The settings are read when the merged `judge` is on and a key is set, whoever set them: a repository that sets `judge` and `judgeKey` while the person's own `judge` is off makes the plugin read the sources, then turn it off; nothing is sent or stored. `judgeBaseUrl` must be https (or loopback http) with no userinfo; a host other than the route's own is the person's own gateway and is used only once attributed as above. The key is in the `Authorization` header only: no `HTTP-Referer`, no `X-Title`, not in the body, a journal, the state, a toast or an error (`judge.ts` strips it from every failure text).
  - Premises the code relies on and cannot check. The key is sent only to the route's host (`openrouter.ai`, `api.typesafe.ai`) or the person's own `judgeBaseUrl`; the typings of `$.http.fetch` (`HttpInit`: `method`, `headers`, `body`, `auth`, `socketPath`) say nothing about whether a redirect is followed with `Authorization` kept, and have no option to refuse one, so the route hosts are trusted not to redirect elsewhere. They have no abort or timeout option either, and a `$` call's time does not count against the hook's 10 s: the only bound on how long a task end waits is the deadline `judge()` races against, which is a `$.clock.after` timer (3 s, `JUDGE_TIMEOUT_MS`, the retry included); a request that outlives it is abandoned (its answer is dropped), not cancelled.
  - Session. One breaker (`createBreaker(() => Date.now())`, three failures, a five-minute pause) and one `JudgeSession` per module instance, shared by every caller; the request timeout is `JUDGE_TIMEOUT_MS` and it is asked once per event. 401/402/403/404 switch the judge off for the session with one toast; 400/422 stop that battery (`batteryKey`: the retry battery with and without `same_failure` are two) for the session; any other failure is journaled and counts toward the breaker. `/pantheon flow status` shows `Judge: <mode>` and whether it is off or paused.
  - Journal and state. Every judged checkpoint is an `escalation` entry (`condition`: `judge_escalated`, `judge_clear`, `judge_stale` or `judge_failed`; `action` the decision the host got; `reason` the numbers that escalated) whose `judge` holds: `checkpoint`, `judgeMode`, `model` and `responseModel`, `requestId`, `usage`, `questionSet` (hash of every question), `uncalibrated`, `attempts`, `ms`, the raw `answers` (probabilities as returned), the `thresholds` used, the `escalation`, `would` (pass 2's action and condition), `applied`, `final`, and `failure` (`reason`, `status`, `off`, `retryAfterMs` and `detail`, up to 200 characters for any failure: for a malformed answer up to 40 characters of the response, for a network failure the host's own error message, which can include the gateway's host name, and for a rejection only the provider's error code, never its message, which can echo the request). Never the key, the state text or the command. `state.lastOutput` keeps, only while the judge is on, a task's last failing check output (the full `redact` with the home and the root, 1500 characters) for the next retry's `same_failure`: it is dropped when the task is done, delivers a pass, or the attempts start over, and by `transact` on the next write whenever the judge is not on (option off, no key, unattributable or refused for the session).
- Privacy: with the merged `judge` off (the default) there is no network request, no key is read and no settings source is read (a repository's settings that turn `judge` on over your off make the merged value on, and the sources are then read to tell, before it is turned off again). With it on and a key set, a request carries only what "What is sent" lists, to the route's host, and the settings sources are read (whole, `env` included) to attribute the options; the journal keeps pass/fail per check, reasons clipped to 600 characters, and the judged checkpoints above; `state.json` keeps the last failing output per task.

## Roster

`roster.ts` joins the native records of the six roles and council seats into eight fixed slots (lead, code-reader, docs-reader, developer, architect, qa, ux, council), with "other agents" when present. The panel groups them as Running (one row per live instance; each council seat has its own) and Idle (exactly one row per role and per council seat with nothing live: the latest run's model, duration and task, a strip of `▰` marks for the role's last four rounds (only with two or more rounds) with `+N` for older ones, `⊘` for a disabled one). A lost run counts as Idle. The council slot carries every configured seat in `seats`.

## Panel

The panel opens at session start. `/pantheon close` closes it; `config` shows the effective configuration and field origins. `doctor` checks the config and pings every role and seat (`ping.ts` plans the targets; `register.tsx` queues the session prompt that calls each agent with `io.after(0, …)`, because the host refuses `prompt.submit` while a `command.run` hook runs). There is no panel configuration.

- `pane.tsx` draws the Agents view only (no tabs).
- Desktop: segments in the former hud plugin's colors, pills as native round-bordered `Box`es (centered, border included in their width; the header's `N running` badge is one, with the close button spaced from it), a pulsing SMIL running dot (image `Svg`, in a fixed 1.5-column slot like the strip's) in the header, the session card and running agent rows, native text and buttons, fixed numeric slots, identity-first agent rows (the model column fits the longest model name, 11 to 24 cells; the terminal keeps 11), a card per section in a native rounded `Box` (colored border, sized to its content, no fixed height or SVG backplate, an even 1-row gap between cards and the same gap under the header when the body has 6 rows or more, and no fold button: a fold stored from the terminal is ignored there; row/column pixels are `ROW_PX` 19 and `COL_PX` 8), and a pane-width "Last 15 minutes" SVG timeline, then a "Session log" card built by `log.ts` from the roster (no hook or persisted state of its own).
- Docked and inline mini: bordered cards per section (colored border) and task-first rows; docked adds the animated rail, mini has none.
- `rail.tsx` and `elapsed.tsx` are surface modules for the animated rail (110 ms frames, only while there is active work) and live clocks. `theme.ts` holds the shared palette, section and role colors and cell helpers.

## Above-prompt strip

`hooks/strip/` holds the modules ported from the former hud plugin (Apache-2.0, built on Token Weather Usage; keep `NOTICE` and `LICENSE-APACHE`), drawn by the `AbovePrompt` entry in `register.tsx` as one rounded box (on desktop, `drawDesktopBox` in `box.ts`: one native `borderStyle="round"` `Box` of three rows, "HUD C": a session row with a pulsing SMIL dot and a ctx `Svg` bar, the 5h and 7d windows side by side (stacked below 66 inner columns), each a label, an exact-px `Svg` bar with a 1.5px elapsed-time tick, the percentage and pace mark, with the time left and the projection in dim text under the bar, and the last-turn or agents row under an `Svg` rule; the proportional font cannot line up glyph edges or space padding, so every column is a fixed-width `Box` and the lowest-priority session parts drop when narrow) or, on the terminal, of at most four rows (`box.ts`): session row, 5h and 7d rows (hud's 10-cell bar plus the `│` clock mark, the same 11 cells on both rows, columns padded to line up, then the projection from `pace.ts`: average rate, or the recent slope when it is 1.5 times faster), and a last row that is either the last-turn receipt (`receipt.ts`) or the running subagents folded in (`agents.ts`). Every width is counted in terminal cells with `theme.ts` (`⚡` takes two). `limitData.history` keeps about 10 `{at, used}` readings per window, saved with each session's readings in the strip store. The receipt counters are per-turn state reset at `turn.start`, fed by the existing `agent.spawn`, `tool.call` (main loop only, result read and passed on as it came) and `turn.complete` handlers; the cost comes from `cost.usd` in `session.measure` and `$.session.usage()`, so the turn's `+$` is the session cost delta during the turn (background agents' spend included), and the agents counted are those the main loop spawned (`!parentAgentId` with an `agentId` in the result), Workflow ones included. Pace readings are stamped with the reading's own time and kept with its `resetsAt`; a new `resetsAt` or a drop in use clears them. Options `abovePrompt` (default true, off hides the strip) and `paceStart`. The next-step suggestions were dropped with hud; users migrating run `/plugin uninstall hud`. Pure modules take host access injected and never touch `$`.

## Prompts and skills

- `prompts/` holds the lead section (`lead.ts`), role prompts and Council Mode.
- `skills/` holds `brainstorm`, `execute`, `debug` and `finish` (`<name>/SKILL.md`). `brainstorm` explores approaches with the person and writes the plan with its `pantheon-flow` block, then asks for `/pantheon flow approve`. `execute` delegates each flow task with `[<taskId>]` to its role, follows the controller's verdicts, and has the developer or ux commit their own task while the lead pushes; without a flow it keeps the plain task-by-task behavior. `finish` requires `/pantheon flow status` complete, then the lead pushes, squashes only when asked or the project's rules say so, and opens the PR/MR itself; validation and review remain with the lead. `scripts/check-consistency.mjs` checks their frontmatter.
- Size budgets. Role prompts (rendered characters) are capped in `tests/roles.test.ts`: developer 2100, ux 3300, qa 1900, docs-reader 1300, architect 1450; code-reader (807) and councillor (1071) must not grow. The lead section is capped in `tests/lead.test.ts` at 4300 with the default config and with each role, or the council, disabled. The skills are not measured by the test runner (it has no filesystem): `execute` must stay at most 8000 bytes and `brainstorm` at most 8500, held by `scripts/check-consistency.mjs` (CI and `make validate`), not by the plan and not by the test runner. Re-measure a skill (`wc -c skills/*/SKILL.md`) after any change to it.
- The rule behind the cuts: what the host denies (withheld tools, `disallowedTools`) or the controller enforces (checks, verdicts, file ownership) is not repeated in a prompt. Never cut: the QA answer format, the `REVIEW:` line, the git and commit rules, and the read-only rules.
