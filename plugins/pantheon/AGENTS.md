# pantheon

Makes the main session the lead in the style of oh-my-opencode-slim. The seven roles and every council seat are native Claude subagents; the configuration chooses each one's model, effort and extra prompt.

IMPORTANT: prompts and panel modules include third-party work. Keep `LICENSE` and the credits and full license text in `NOTICE`.

## Roles

- Roles and seats are registered as native `pantheon:<role>` or `pantheon:councillor-<seat>` agents with `$.agent.register` (no tool list, so they inherit the session's tools; architect, qa and councillors get `disallowedTools` Edit, Write and NotebookEdit; code-reader, docs-reader, architect, qa, git and councillors also get Agent; developer and ux get none), and hidden by an `agent.offer` guard when disabled.
- Developer writes all code (UI code and logic included) and runs scripts, test batteries and API calls within the brief, returning short results; no external research or sub-delegation. It tells the lead when a task is look and feel (guidance, not a refusal). Developer and ux commit their own task's files after the checks pass (`git add -- <paths>`, `git commit -m "<type>(<scope>): <summary> [<taskId>]" -- <paths>`; never `-A`, `.`, `--no-verify` or `--amend`, no AI attribution, retry once on `index.lock`) and never push, rebase, reset, merge, switch or stash; the lead pushes.
- UX owns look and feel (layout, hierarchy, color, spacing, motion, UI copy), makes mockups and throwaway prototypes (scratchpad, never committed) when the direction is open, and implements the chosen one, keeping the design criteria of the former designer; the split with developer is by kind of work, not by file extension. Docs-reader reads external docs and research; it does not write docs. Architect covers architecture, debugging, review and simplification. QA runs what was built and returns `C<n>: pass|fail — <evidence>` per acceptance criterion plus a final `QA: pass|fail` (partial coverage is a fail); it never fixes code or runs side effects and writes only in the session scratchpad through Bash.
- Developer, ux and git may write within their assigned scope. The git role executes squash, PR/MR creation and repository state changes (checkout, switch, worktree, stash) from the lead's brief; the lead decides the included changes, branch, base, squash/PR choices and task commit range, pushes, and owns validation. Git follows repository conventions and templates, uses `gh` or `glab`, and reports SHAs, PR/MR URLs and refusals; it does not push.
- Git's fixed refusals cover modifying default or protected branches (including main, master, develop, release and release/*), unverified branch protection, force push without `--force-with-lease`, PR/MR merges, remote branch deletion, history rewrites outside an explicit task commit range, and work outside the task.

## Config

- `config.ts` merges built-in defaults, `~/.claude/pantheon.json` and `<repo>/.claude/pantheon.json` field by field: `agents.<role>` and `council.seats.<seat>` take `model`, `effort` and `prompt`; `disabledAgents` is a union. Models must be Claude models (`models.ts`).
- Fields of the Codex and profile era (`profile`, `profiles`, `sandboxCap`, `noNetwork`, `foregroundMinutes`, an entry's `engine` or `sandbox`) and the old role names (`explorer`, `librarian`, `executor`, `designer`, `oracle`, `fixer`) fail to load with one message listing them saying what to do.

## Edit gate

- `decisions.ts` is pure and holds the local size and path rules (`rulesVerdict`); `gate.ts` is pure and builds edit context, exemptions and messages. Pure modules never touch `$`; `register.tsx` owns host access, path resolution and the Proceed/Cancel hold. The gate makes no network request and reads no API key: with metadata only, "is this edit trivial?" is a code decision.
- The `tool.call` hook matches `Edit`, `Write` and `NotebookEdit`, main session only. It is registered after the tracking handler, which wraps it and observes the settled result once: held calls are not counted early and denials do not count as successful edits.
- Plugin option: `gate` defaults to false. Rules: a sensitive path (workflow, migration, manifest, lockfile) always asks; more than 3 files, or more than 100 lines (the known added plus removed lines, a lower bound when a Write leaves the removed count unknown), denies; a single-file change of at most 5 lines, or a doc change of at most 20, allows; unknown counts and everything else ask. An ask holds the call for Proceed/Cancel only when `session.start` reports `isInteractive: true` and a non-null `surface`, otherwise it denies without a hold. Recovery covers evaluation only; forwarding failures propagate to the engine without a second confirmation.
- Exemptions are `<repo>/.pantheon/plans/**` (`.pantheon/flow/**`, which holds the approval and the state the flow trusts, is not exempt and always asks), `~/.claude/plans/**`, `~/.claude/projects/*/memory/**` and the current user's session scratchpad; the rest of `~/.claude` is gated. Decisions are per call, with no per-turn accumulator or Bash write detection.

## Tracking and state

- `tracking.ts` holds pure reducers for native subagents and the main session, plus tool-input redaction.
- The tracking hooks (`turn.start`, `turn.step`, `turn.complete`, `session.measure`, `agent.spawn`, `tool.call`) only watch and pass events on unchanged.
- `pantheon.natives`, `pantheon.session` (with the ledger cost) and `pantheon.view` (the folded groups) live in `$.state`, written through queues that keep only the latest pending snapshot.
- The panel shows one toast per session the first time saving the panel state (agents, session or folded groups) fails.
- `register.tsx` builds host closures in each hook because `$` cannot be stored.

## Flow

The decision flow is wired by `register.tsx` over pure modules in `hooks/flow/`: `plan.ts` (the contract), `policy.ts` (the reducer), `store.ts` (files), `checks.ts` (approved checks through an injected runner, passes with a memo and a deadline), `verdicts.ts` (QA `C<n>:` lines and `QA:`, the architect's `REVIEW:`) and `controller.ts` (orchestration), plus the git gate: `gitgate.ts` (shell parsing, per-actor policy, adapted from branch-guard), `gitguard.ts` (the lead's current branch, a developer's ownership and task id, over it) and `gitjournal.ts` (its journal entry). The judge is not wired yet (T9): `controller.ts`'s `step` is the seam, passing `judgment: undefined`.

- `controller.ts` takes a `Ctx` with injected `fs` (read returns undefined only when missing), `run`, `now`, `root`, `mode`, enabled roles, `list`, `serial(planId)` and the check `memo`, and never touches `$`. Its entry points are `stopFlow`, `taskEnded`, `reviewed`, `inspectSpawn`, `inspectIsolation`, `mainEdit`, `humanPrompt`, `noteOwnership`, `flowTaskFiles` and the commands (`approvePlan`, `controlFlow`, `flowStatus`). Each one finds the plan through `.pantheon/flow/active`, finds the flow in force (below), loads or creates the state (ledger applied, a changed flow rebased and `withMode`), settles the plan file's edit, runs `decide` then `applyMode`, saves and journals.
- Writes to a plan's files are one `createSerial()` job (`transact`: load, decide, ledger, save, journal). Long work, the checks and git, runs before the job, because a hook waiting for the queue spends its own 10 s budget. Checks run only for the flow in force. A decision made on check results is dropped (`transactAt`) when an approval or an adoption moved the flow in force while the checks ran: results of another command must never settle a task. Every entry point is wrapped by `guarded`: an error warns, journals when the plan is known and answers allow (fail open); `off` returns before anything is read.
- Checks run as `env -u OPENROUTER_API_KEY -u TYPESAFE_API_KEY -- <argv>` (the host can only set variables, not unset them; `--` ends `env`'s options, which macOS and GNU `env` both accept, and `plan.ts` refuses an `argv[0]` that starts with `-` or contains `=`). Only those two judge keys are removed: the check inherits everything else. `passed: null` means the command timed out or `env` could not exec it (exit 126/127); any other rejection of the runner throws `CheckUnrunnable`, which the controller answers with allow, a warning and a `check_unrunnable` journal note, charging no attempt.
- A check pass (`createCheckPass`) reuses a pass while the tree snapshot is the one it was produced on (`treeSnapshot`: `git rev-parse HEAD`, a git-computed hash of `git diff HEAD` and of the untracked files' names and contents up to 300, never `.pantheon/`). Only a pass is remembered (a fail, a `null` or an unverified check runs again), and only when the snapshot after the pass equals the one before it: a check that changed the tree did not pass on the tree it leaves. A Stop evaluation has `STOP_DEADLINE_MS` (120 s) that bounds its snapshot git calls too (each is cut to the time left): past it no check starts, the running one is cut to the time left and what did not run is unverified (no result, never a fail, no attempt) with a `checks_unverified` note; in enforce `StopOutcome.context` tells the lead which task in progress (active or awaiting) had checks that never ran, and the Stop hook returns it as `additionalContext`. The memo lives in memory, in `register`'s closure.
- A QA snapshot is `treeSnapshot` limited to the task's `files`: the names git lists for them (`ls-files --cached --others`), the ones deleted and the content of each (`hash-object --stdin-paths`; past 2000 files, the diff). Only its digest is compared, so an unrelated commit, QA's own artifacts or a commit of those files with the same content do not void a receipt.
- Hooks in `register.tsx`: `agent.spawn` (matcher: a description starting `[`) links the agent id to its task in the `pantheon.flowAgents` state value (task, kind work|review|diagnosis, reviewer, end count at spawn, denials, files, QA snapshot, `root` for an inherited link; the newest 48) and enforces decisions 16 and 17, and in enforce only appends the approved criteria to a QA agent's prompt (shadow rewrites nothing; a delegation with no plan in force links nothing and holds nobody back); a second `agent.spawn` hook (matcher: a `parentAgentId`) gives a subagent of a work agent the parent's task and files; `tool.call` on `Edit|Write|NotebookEdit` with an `agentId` enforces ownership from the link's files, with the path and root resolved by the host as the gate does and only this session's scratchpad exempt (the hook has a `.catch`: when it did not finish, `flowWriteFallback` refuses a write by a linked work agent in enforce); the unmatched `tool.call` hook (tracking) reports a main-session edit to `mainEdit` after the settled result (its `resolve` asks the host for the real root and path once a plan is in force) and appends its text to the result; `tool.call` on `Bash|Monitor` is the git gate (below); `tool.call` on `Agent` refuses `isolation` on a `[T]` delegation, then appends the verdict as `context` of the result; `prompt.submit` for origin `task-notification` attaches the verdict as context (`parseNotification` needs `<task-id>` and `<status>` in the envelope before `<result>`), and for `composer|bridge|sdk` it refills the budget and re-injects state; `classic.Stop` runs after `next(e)` (it leaves another hook's block alone), counts only `subagent` and `workflow` background tasks and returns `{ block }` only in enforce. The engine refuses the same event twice without a matcher, so each of these has a distinct one. Hooks act only after `session.start` found the root: the flow never runs a command to look for it.
- Git gate (decision 12), over `gitgate.ts`, `gitguard.ts` and `gitjournal.ts`, on the `tool.call` hook for `Bash|Monitor` (`gitDenial` in `register.tsx`; a `Monitor` with no `command` is a WebSocket and is skipped). It is a guardrail that reads the text of a command, not a security boundary: the person's own deny rules and the server's branch protection are the boundary, and the gate does not chase every exotic form.
  - `gitgate.ts` classifies a shell line (`classifyGitCommand`: segments with verb, paths, message text, `-c` keys, push options and the separator before each, `gh`/`glab` calls, hidden git) and `gitAllowed(actor, command, owns, { gitRole, protected, found })` decides per actor. It is pure and does not know the checked-out branch. An unquoted `#` that starts a word is a comment; `timeout`, `gtimeout`, `nice`, `ionice`, `stdbuf`, `setsid`, `caffeinate` and `arch` are transparent wrappers; `xargs` and `find -exec` count as hidden git only when what they run is a git, a shell or a wrapper; any other command that is followed by a `git` (or `gh`, `glab`) and a verb or option (`op run -- git push`, `mise exec -- …`, `xcrun`, `flock f`) is hidden git, unless it is a reader (`echo`, `grep`, `ls`…); `eval "$X"` counts when the line mentions git; long options are read by unambiguous prefix (`--rep` is `--repo`).
  - For every actor, the git role included: a hidden git (opaque) is denied; `-c` and `--config-env` may set only `color.*`, `core.quotepath`, `advice.*`, `i18n.*`, `user.name` and `user.email`; environment that skips hooks or runs a program (`HOOK_ENV`: hook skips, `GIT_DIR`, `GIT_CONFIG*`, `GIT_SSH*`, `GIT_ASKPASS`, `GIT_EXTERNAL_DIFF`, `GIT_PROXY_COMMAND`, editors, `GIT_PAGER`, `PAGER`, `EDITOR`, `VISUAL`, `HOME`, `XDG_CONFIG_HOME`, `GIT_TEMPLATE_DIR`, and any export it cannot read) is denied; so are `ext::` and `fd::` URLs and `--upload-pack`, `--receive-pack` and `--exec` on push, fetch, pull, clone, ls-remote and archive (a rebase's `--exec` is read apart), and a `merge_request.*` push option.
  - The forge: `pr`, `mr`, `repo`, `api` and `release` are state-changing unless a read action; `issue`, `run`, `workflow`, `ci` and the other groups gh and glab have pass; `alias set|import` and `extension install|upgrade|exec` are denied for every actor, and a group neither list knows (an alias such as `gh mm` can be `pr merge --admin`) is held as state-changing, so the lead is denied and the git role refused. The git role, and a lead acting as it, may not merge, delete a repository, `repo sync --force`, or change `/git/refs`, `/branches` (protection included), `/merges`, `/rulesets`, `/contents`, `repository/{branches,files,commits}` or run a GraphQL mutation (or a query read from a file or stdin) through `api` (a method or fields make it a write; `-X GET` with fields is a read); nor name a protected branch in `branch -d|-D|-m|-M|-c|-C|-f`, `update-ref` (`--stdin` is refused), `tag -d|-f`, `checkout -b|-B`, `switch -c|-C` or `worktree add -b|-B`; nor write `alias.*`, `push.*`, `url.*`, `credential.*`, `include.path`, `includeIf.*.path`, `core.hooksPath|sshCommand|pager|editor|…`, `remote.*.push|pushurl|mirror|…` or `branch.*.remote|merge|pushremote` with `git config` (every loose word is tested as the key, so `set` and `--file x` do not hide it).
  - `gitguard.ts` (`gitGate`, `usesGit`, `actorOfType`, `cwdOfAgent`) wraps it with what the text cannot say, through an injected `GitHost` (`owned`, `branch`, `config`). A push that does not write `src:dst` for every refspec (none at all, a source alone, `HEAD` or `@`; not `--tags` alone) leaves the destination to git, which the push settings can send elsewhere (`remote.*.push`, `push.default=upstream` on a branch that tracks another): the settings `host.config` reads (`remote.*.push`, `remote.*.mirror` and `push.default` of `upstream`, `tracking` or `matching`) make it unknown, and a lookup that fails denies. With no refspec, or `HEAD`/`@`, it also goes to the branch `host.branch` reads. The git role, and a lead acting as it, are held to the current branch for `commit`, `merge`, `rebase`, `reset`, `cherry-pick`, `revert`, `am`, `pull` and `update-ref HEAD`. A protected branch (`PROTECTED_DEFAULT`: main, master, develop, release, release/*; `heads/` and `refs/heads/` stripped) or an unknown one is denied. Unknown is a detached HEAD, git failing, a `cd`, `--git-dir` or non-literal `-C`, a destination that is not literal, more than 4 places, or a branch-changing git earlier on the line: `checkout -b X`, `switch -c X` and `switch X` name the branch for what follows only when `&&` joins them (after `;`, `||`, a pipe or a newline the change may have failed), and any other change leaves it unknown. A developer's commit must carry `[<taskId>]` in `-m` or `--message` (not `--author` or a trailer).
  - `register.tsx` supplies the actor and the host. No `agentId` is `lead`; an agent whose link is a work task with `files` is `developer`, and `host.owned` runs each path through `flowOwnership` (links followed, the same resolution as write ownership). Any other agent is held by its type from `$.agent.list()` (`actorOfType`): `pantheon:developer` and `pantheon:ux` with no link are `developer`/`ux` with every path their own and no task id asked (verbs and flags unchanged), `pantheon:git` is `git`, `code-reader`, `docs-reader`, `architect`, `qa` and council seats are read-only, and every other agent (general-purpose, Explore, one the engine does not list) gets the lead's rules. A line that runs no git is classified once and does no lookup.
  - The lookups run where the agent works. The Bash event does not say, so two small hooks read it at the spawn: an `agent.spawn` hook (matcher `tool_use_id`) keeps the call's `cwd`, and a `tool.call` hook on an `Agent` call with `isolation` marks the agent it starts. `cwdOfAgent` walks the parents: the main loop and an agent chain that set none use the session's, one with a `cwd` runs there, and an isolated agent (a worktree the engine makes) or one nothing accounts for is not knowable, so its lookups are "unknown" and denied.
  - The branch and the settings are read with literal `$.process.run` calls of at most 5 s (`git [-C dir] rev-parse --abbrev-ref HEAD` and `git [-C dir] config --get-regexp '^(remote\..*\.(push|mirror)|push\.default)$'`, whose exit 1 is "none set"); a failure is "unknown", while an error anywhere else fails open (`flowFailed`, `next` outside the `try`). It follows the mode (`off` returns before anything is read, shadow journals `wouldBe: block`, enforce returns `{ deny: "[Pantheon flow] <reason>" }`) and needs no plan or approval.
  - `gitjournal.ts` writes a `decision` entry (`event: git`, `condition: git_gate`, `detail: <actor>: <git commands without arguments>`, never the command text; reason and detail go through `redactSecrets`, and a forge reason names only the tool, group and action) into the journal of `activePlanId` (the id the plan was approved under) through that plan's serial queue. With no active plan nothing is written: shadow outside a plan is silent, and enforce's denial still reaches the model.
  - Known limits (a guardrail on top of the person's deny rules and server-side protection): a script written and then run (`./push.sh`, `make`, `npm run`, `node -e`, `python -c`, `curl` to the forge API, `eval` of a value read from a file); direct writes to `.git/config`, hooks or refs by an edit tool or `sed`; `--recurse-submodules=on-demand`; `git fetch origin x:main` updating a local protected branch; `gh workflow run` (a workflow can push or merge); `PATH` and shell startup files; any command that runs another through an option the reader list does not know. Edit `gitgate.ts` only with its table tests (`flow-gitgate.test.ts`); the wiring is tested in `flow-gitguard.test.ts` and `flow-gitgate-register.test.ts`.
- `$.state` reads inside a dispatch are snapshots, so the links are also kept in memory (`FlowRuntime.links`); an agent's first write finds a link not yet stored by waiting (up to 2 s) for the delegations in flight (`FlowRuntime.pending`), then by asking `$.agent.list()` (its `[T]` description or its `parentId`). Only the first level waits (one wait of at most 2 s, not one per level of parents); the lookup is `inspectSpawn` with `lookup`, which journals and refuses nothing. Agents found to belong to no task are remembered; `/pantheon flow resume` forgets that, and refreshes the links' `files` from the approved plan.
- Approval and plan edits (decision 19). Nothing under `.pantheon/flow/` says what the person approved: any edit can write those files. The approval is the host's record (`Ctx.attest`, backed by `$.store` in `register.tsx`, key `flow.attest.<sha256(root)[:32]>.<planId>`, contract `FlowAttest` in `types/index.d.ts`): `{ approvedHash, adoptedHash?, snapshotHash, adopted? }`, written only by `approvePlan` and by an adoption `amend` accepted, before the snapshot (record, `approved.json`, state, `active.json`, pointer). A plan stands approved only while `approved.json` is valid, hashes to what it records and is exactly what the record names (`matchesAttest`); the state is progress and is brought back to that approval (a lost or forged state restarts its tasks from the approved flow). Without a host store (`attest` absent) the state's `approvedHash` must agree with the snapshot, which a forged file also satisfies: `register.tsx` always passes it. A store that rejects `get` is read as no record (`tampered`, never approved, never an error to fail open on), and one that rejects `set` (a store over 4 MiB, say) makes the approval or adoption fail before anything else is written.
  - A plan that was approved but whose snapshot is missing, unreadable, edited or unattested, or whose state records an approval nothing attests (a state from before attestation, a cleared store: one `/pantheon flow approve` after upgrading) is `tampered`, never "unapproved": no check of it runs, the state keeps `approvedHash` (a lost approval would be a switch), the Stop is held in enforce with "the approved snapshot changed outside /pantheon flow approve; run /pantheon flow approve" (spending the budget a failing check does, then let through; a human prompt refills it and tells the lead; pause, stop and background work are respected) and shadow journals `snapshot_tampered` once. Restoring the file as attested resumes enforcement without an approve.
  - An edit never switches enforcement off. `locate` compares the file with the flow in force; `prepare` runs `amend` (plan.ts, pure) through a per-process cache keyed by everything it reads, and adopts the edit only when it is purely additive (the allowlist is the comment above `amend`; any other change, or a part of an edit that is not additive, makes the whole edit wait): `rebase` onto the adopted flow keeps `approvedHash` and sets `adoptedHash`, the record and `approved.json` are rewritten, and a `kind: amendment` journal entry (`amendment_adopted`, with both hashes) is written. What waits is journaled once per content (`amendment_pending`, the reasons capped at 20; `state.seenEdits` is the bounded set of keys), shown by `/pantheon flow status` ("N waiting for /pantheon flow approve", with reasons) and in the reinjected context; a file that does not validate is journaled once per content (`amendment_invalid`) and changes nothing. The diff base is the flow in force, so adoptions chain; every id the plan has had (`state.seenIds`, bounded, seeded from the journal and the ledger once) is never reused. An adoption whose new work needs a disabled role waits, as approve would refuse it. Tasks adopted over the approval are listed in the record: status and the reinjection mark them as the lead's, not the person's.
  - `validateFlow` bounds a plan (`PLAN_LIMITS`: 100 tasks, 50 files, 20 checks and 20 criteria per task, 64 argv words, 300-character patterns with at most 8 wildcards, a 256 KB block) and refuses `files` whose first segment is `.pantheon`, `.git` or `.claude`, so no amendment can adopt them; `ownershipVerdict` never grants `.pantheon/flow/**`, `.git/**` or `.claude/**` whatever the patterns match, and the edit gate does not exempt `.pantheon/flow/**` (only `.pantheon/plans/**`) and always asks for it. A new task may reuse only the commands of regular tasks (not an onFail branch's or a side effect's), and overlaps no task that is not done, nor a done `risk` task, nor a done task unless it is `risk` itself.
  - A decision made on results gathered for another flow than the one in force is dropped (`transactAt`) and the evaluation starts over once; changing again, Stop is held once saying so and a task end or review asks to be repeated.
  - `mainEdit` on the plan file itself returns the outcome for the lead in enforce (adopted, waiting with reasons, or invalid). `/pantheon flow approve` replaces the snapshot with the current block, keeps the progress of tasks still in it, and clears `adoptedHash` and what waited. Journal kind `escalation` is reserved for the judge (T9w).
- Shadow journals what enforce would do (`wouldBe`) and attaches, denies and blocks nothing. Plugin option `flow` (`off`, `shadow` default, `enforce`).
- `/pantheon flow status|approve [path]|pause|resume|stop` is handled in the `pantheon` `command.run` hook; `approve` writes the snapshot, the state and the pointer, and records the hash, and `resume` clears a pause or stop and the attempts of unfinished tasks.
- Privacy: no network, no key; the journal keeps pass/fail per check and reasons clipped to 600 characters.

## Roster

`roster.ts` joins the native records of the seven roles and council seats into nine fixed slots (lead, code-reader, docs-reader, developer, architect, qa, ux, git, council), with "other agents" when present. The panel groups them as Running (one row per live instance; each council seat has its own) and Idle (exactly one row per role and per council seat with nothing live: the latest run's model, duration and task, a strip of `▰` marks for the role's last four rounds (only with two or more rounds) with `+N` for older ones, `⊘` for a disabled one). A lost run counts as Idle. The council slot carries every configured seat in `seats`.

## Panel

The panel opens at session start. `/pantheon close` closes it; `config` shows the effective configuration and field origins. `doctor` checks the config and pings every role and seat (`ping.ts` plans the targets; `register.tsx` queues the session prompt that calls each agent with `io.after(0, …)`, because the host refuses `prompt.submit` while a `command.run` hook runs). There is no panel configuration.

- `pane.tsx` draws the Agents view only (no tabs).
- Desktop: segments in the former hud plugin's colors, pills as native round-bordered `Box`es (centered, border included in their width; the header's `N running` badge is one, with the close button spaced from it), a pulsing SMIL running dot (image `Svg`, in a fixed 1.5-column slot like the strip's) in the header, the session card and running agent rows, native text and buttons, fixed numeric slots, identity-first agent rows (the model column fits the longest model name, 11 to 24 cells; the terminal keeps 11), a card per section in a native rounded `Box` (colored border, sized to its content, no fixed height or SVG backplate, an even 1-row gap between cards and the same gap under the header when the body has 6 rows or more, and no fold button: a fold stored from the terminal is ignored there; row/column pixels are `ROW_PX` 19 and `COL_PX` 8), and a pane-width "Last 15 minutes" SVG timeline, then a "Session log" card built by `log.ts` from the roster (no hook or persisted state of its own).
- Docked and inline mini: bordered cards per section (colored border) and task-first rows; docked adds the animated rail, mini has none.
- `rail.tsx` and `elapsed.tsx` are surface modules for the animated rail (110 ms frames, only while there is active work) and live clocks. `theme.ts` holds the shared palette, section and role colors and cell helpers.

## Above-prompt strip

`hooks/strip/` holds the modules ported from the former hud plugin (Apache-2.0, built on Token Weather Usage; keep `NOTICE` and `LICENSE-APACHE`), drawn by the `AbovePrompt` entry in `register.tsx` as one rounded box (on desktop, `drawDesktopBox` in `box.ts`: one native `borderStyle="round"` `Box` of three rows, "HUD C": a session row with a pulsing SMIL dot and a ctx `Svg` bar, the 5h and 7d windows side by side (stacked below 66 inner columns), each a label, an exact-px `Svg` bar with a 1.5px elapsed-time tick, the percentage and pace mark, with the time left and the projection in dim text under the bar, and the last-turn or agents row under an `Svg` rule; the proportional font cannot line up glyph edges or space padding, so every column is a fixed-width `Box` and the lowest-priority session parts drop when narrow) or, on the terminal, of at most four rows (`box.ts`): session row, 5h and 7d rows (hud's 10-cell bar plus the `│` clock mark, the same 11 cells on both rows, columns padded to line up, then the projection from `pace.ts`: average rate, or the recent slope when it is 1.5 times faster), and a last row that is either the last-turn receipt (`receipt.ts`) or the running subagents folded in (`agents.ts`). Every width is counted in terminal cells with `theme.ts` (`⚡` takes two). `limitData.history` keeps about 10 `{at, used}` readings per window, saved with each session's readings in the strip store. The receipt counters are per-turn state reset at `turn.start`, fed by the existing `agent.spawn`, `tool.call` (main loop only, result read and passed on as it came) and `turn.complete` handlers; the cost comes from `cost.usd` in `session.measure` and `$.session.usage()`, so the turn's `+$` is the session cost delta during the turn (background agents' spend included), and the agents counted are those the main loop spawned (`!parentAgentId` with an `agentId` in the result), Workflow ones included. Pace readings are stamped with the reading's own time and kept with its `resetsAt`; a new `resetsAt` or a drop in use clears them. Options `abovePrompt` (default true, off hides the strip) and `paceStart`. The next-step suggestions were dropped with hud; users migrating run `/plugin uninstall hud`. Pure modules take host access injected and never touch `$`.

## Prompts and skills

- `prompts/` holds the lead section (`lead.ts`), role prompts and Council Mode.
- `skills/` holds `grill`, `execute`, `debug` and `finish` (`<name>/SKILL.md`). `execute` has the developer or ux commit their own task, the lead pushes, and `finish` has git open the PR/MR from a lead brief; validation and review remain with the lead. `scripts/check-consistency.mjs` checks their frontmatter.
